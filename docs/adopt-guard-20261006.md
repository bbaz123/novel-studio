# 采纳事故 · 零损失护栏挡住正文（2026-10-06）

> 作者报障原文：
> 「覆盖仍未成功（正文没有被改动）：采纳失败（已整体回滚，未写入任何内容）：
> 旧提案未全部入账（达标 14/13，护栏拦下 #1）——已整次回滚，为什么会被护栏挡下，
> 我不是说过，一切以用户行为为准，未保存的内容弹窗告知用户：旧内容是否保存？选项：是，否；
> 然后用户执行的内容完整出现在正文里」

本文记录取证、根因、修复与新语义。**所有结论都可在活库上复算**（见 §5）。

---

## 1. 症状

作者点「应用到正文 / 以我的当前内容覆盖」后，正文一字未变，界面报
`采纳失败（已整体回滚，未写入任何内容）：旧提案未全部入账（达标 14/13，护栏拦下 #1）`。

计数 `14/13` 本身就是自相矛盾的：**落地条数怎么会多于勾选条数**。

## 2. 根因（三条，缺一条都不会发生这次回滚）

### 2.1 提案 id 在两表之间同号 —— 作者勾选被静默扩大

`story_event_proposals` 与 `story_memory_proposals` 是**两张表、各自独立的 id 序列**，都从 1 开始。
界面复选框只写裸 id（`public/app.js` 的 `proposalItemHtml`：`data-proposal-id="${p.id}"`），
结果弹窗把两类提案混在一个列表里渲染、**默认全选**。

事故现场（作品 #18）：pending 为「事件 #1–#13」+「长期记忆 #1、#2」。
界面显示 15 个勾选框，送出的裸 id 去重后只有 13 个 —— `事件 #1` 与 `记忆 #1` 是同一个数字。

服务端旧实现拿这个裸 id 列表去**两张表各查一遍**，于是：

| 表 | 命中 | 结果 |
| --- | --- | --- |
| 事件 | #1–#13（13 条） | 全部入账 |
| 长期记忆 | #1、#2（2 条） | #2 用 delta 合成摘要后**被写入**；#1 被零损失护栏拦下 |

`appliedCount = 13 + 1 = 14`，而 `legacySel.length = 13` → `14 !== 13`。
**作者从未勾选的那两条记忆提案参与了他这一次采纳。**

### 2.2 零损失护栏确实拒绝了记忆 #1

记忆 #1 是模型自压缩提案（`guard='agent'`，2026-10-01 创建），只覆盖「第 1–4 章」共 776 字；
而护栏按**全书正文**推导"出场过的实体必须全部保留"。实测判据：

```
ok=false
实体覆盖率 56% 低于下限 100%（丢失 7/16）：
夜鸦、陈牧野、顾青山、超凡联盟（超盟）、海澜市第三高级中学（海澜三中）、黑潮组织、深海遗迹·零号（禁地一）
```

### 2.3 正文写入被绑死在"提案全有或全无"里 —— 这是真正挡住作者的那一条

旧实现在同一个事务里依次做：状态提案 → 旧提案入账 → **写正文**。
第 2 步抛错就直接回滚，第 3 步的正文**一个字都没执行到**。
于是"一条与本章无关的长期记忆提案没过护栏"，变成了"作者的正文写不进去"。

## 3. 修复

### F1 · 提案引用带来源类型（消除同号歧义）

- 新契约：`legacy_proposal_refs: ["event:12", "memory:12"]`（或 `{type,id}` 对象）。
- 前端复选框改为写 `data-proposal-ref="event:12"`（保留 `data-proposal-id` 兼容），
  三个读取点统一走 `collectCheckedProposalRefs()` / `proposalIdsOfRefs()`。
- 服务端 `normalizeProposalRefs()` + `proposalRowOfRef()` **单点解析**：
  带类型的引用只认自己那张表；裸 id（旧客户端）按"事件优先"解析成**唯一一行**，不再扩散。
- `refs` 是数组时**以 refs 为准**，不再与裸 ids 求并集（否则"记忆 #1 + 裸 id 1"会同时命中两行）。
- 幂等键 `norm` 里补入带类型的引用：光有裸 id 时 `event:1` 与 `memory:1` 指纹会一样。

### F2 · 护栏不得挡住正文

- 完整性判据从"落地条数 === 勾选条数"改为"**每一条引用都有明确结局**"：
  `applied + rejected + guard_failed === selected`。
  （旧判据把"空提案按拒绝处理"这条正常路径算成了不完整，本身就会假红。）
- 被零损失护栏拦下的记忆提案**不再回滚整次采纳**：保留 `pending` 待作者修正，
  原因随 `adopt.legacy.guard_failed` 如实回包，由界面讲清楚"正文已写入 + 哪条没入账 + 缺哪些实体"。
- 仍会让整次回滚的只剩真正的完整性失败与陈旧检查（引用取不到 / 状态已变 / 基线 hash 不符）。
- 前端 `handleAdoptFailure` 只对**真并发/基线冲突**弹"以我的当前内容覆盖"框
  （`ADOPT_CONFLICT_RE`）；其余拒绝如实报原文案，不再把护栏错误包装成并发冲突把作者引到错出口。

### F3 · 「旧内容是否保存？」是 / 否

- 正文即将被覆盖、且这一章还有**没落盘**的旧内容时，弹出不可点遮罩关闭的确认框：
  - **是** → 把这一版存进本章历史版本（`POST /api/chapter_versions`，不改正文），再写入新内容；
  - **否** → 不为这一版额外留档，直接写入新内容。
- **两个答案都不拦操作**：无论选哪个，新内容都必须完整写进正文。
- 无论选哪个，都把那一次在途旧稿从本地待保存队列撤下 —— 否则自动重试随后会把它落盘，
  把刚采纳的新正文**倒回旧稿**。
- 被 ✕ / 遮罩关掉时按**「是」**收口：误触关闭最不该发生的事就是弄丢作者手里那一版。
- 只在**确实有未保存内容**时才问；没有时不打扰（不回退 2026-10-05「提示只属于导航」那条修正）。
