## 一、发现的失误与修复

### 失误 1（严重）：我实现了「分层追踪」的接口，却从未接线 —— 死代码

**现象**
`debug-trace.js` 导出了 `bumpTool()`（高频函数只累计次数与总耗时的机制），`server.js` 也把它写进了 import 列表，
但**全仓库没有任何一处调用它**。诊断命令输出：

```
bumpTool   外部引用 1     ← 仅 import，0 处调用
```

**影响**
用户在需求澄清第 10 题明确选择「B 分层追踪：业务主干全量记、高频工具函数只记次数+累计耗时」。
实际交付里只有「主干全量」这一半，另一半（高频聚合）是空的 —— 也就是说，
一项用户明确选定的功能**没有实现**，而我却在 README 里写了「高频工具函数只累计调用次数 + 合计耗时」，
属于把未实现的能力写进了文档。

**根因**
我把「导出 API」当成了「功能已完成」。写 `bumpTool` 时想的是"以后有需要再在各处调用"，
结果提交时没有回头核对「用户选的每一项是否都有真实调用点」。
另外 `api-test-suite.mjs` 里也没有任何断言覆盖这条路径，测试全绿给了我虚假的完成感。

**修复**
1. `server.js` 的 `prepare()`（真正的后端高频热路径，一次操作可发生上百次）接入：
   - 缓存命中 → `bumpTool('prepare 语句（缓存命中）', 0)`
   - 缓存未命中 → `bumpTool('prepare 语句（缓存未命中）', 耗时)`
2. `/api/debug/ops` 本来就返回 `tools` 聚合表，但前端从未展示 → 在追踪页新增
   「高频函数累计」折叠面板（`refreshTraceTools()`），显示「N 类 / 共 M 次」与逐类次数、合计耗时。
3. 新增断言 `I3y`/`I3z`：验证累计表非空、带次数与合计耗时。

**验证证据**
```
PASS  I3y 高频函数累计表非空（bumpTool 已接线）  — kinds=2 prepare 语句（缓存命中） ×13
PASS  I3z 累计表带次数与合计耗时  — {"name":"prepare 语句（缓存命中）","count":13,"cost_ms":0}
```

### 失误 2（中等）：心跳超时余量太小，会把「切到别的标签页」误判成「页面已关闭」

**现象**
前端每 10 秒 ping 一次，后端 `checkStaleTracing` 超时设为 **20 秒**（仅 2× 余量）。

**影响**
浏览器会把**后台标签页**的定时器节流到约 1 次/分钟。用户只要切到别的标签页超过 20 秒，
后端就会判定「页面已关闭」并调用 `stopTracing('stale')` 停止录制。
结果是：用户开着录制去查资料、切回来继续写作，录制早已静默停止 —— 而界面上按钮仍显示「● 录制中」，
造成"以为在录、其实没录"的静默数据丢失。这是本功能最影响可用性的缺陷。

**根因**
我按「超时 = 2 × ping 间隔」这个想当然的公式取值，**没有考虑浏览器对后台标签页的定时器节流**。
这是一个已知的 Web 平台行为，我在写前端 ping 时甚至注释过另一个相关的节流问题
（`app.js` 里页面隐藏时跳过卡顿采样的既有代码），却没想到它会反噬我自己新写的机制。

**修复**
- `checkStaleTracing` 默认超时 20s → **90s**（9× ping 间隔），并写明为何取这个值
- `server.js` 的检查间隔 5s → 15s（与 90s 阈值匹配，减少无谓唤醒）
- 注释里明确记录「后台标签页节流到约 1 次/分钟」这一约束，避免以后又被改回去

### 失误 3（轻微）：4 个导出符号无人使用，其中 2 个是纯死代码

**现象**（诊断输出）
```
currentOp        外部引用 0   ← 内部使用，导出多余
setHttpStatus    外部引用 0   ← 完全未使用（连内部都没用）
traceFilePath    外部引用 0   ← 完全未使用
isRecording      外部引用 1   ← 仅导入，0 处调用（server.js import 了却不用）
```

**影响**
误导后续维护者以为存在这些能力；`server.js` 的 import 列表有一条永不使用的条目。

**根因**
先写"完整 API 面"再实现调用点的习惯，收尾时没有做一次「导出符号 → 实际调用点」的对账。

**修复**
- 删除 `setHttpStatus`、`traceFilePath`、`isRecording`
- `currentOp` 保留但去掉 `export`（它确实被内部 4 处调用）
- `server.js` import 列表移除 `isRecording`

### 失误 4（文档准确性）：README 对落盘形态的描述与原方案不一致，但未在文档里说明取舍

**现象**
原方案写的是「明细落 JSONL + 摘要入 SQLite `debug_traces` 表」。实施时我判断 JSONL 已经自描述
（`session-start` / `op-end` / `session-end` 三段记录已含全部摘要），额外建表是重复存储，于是**没建表**。
这个取舍我在对话里口头说明了，但 README 里只写了 JSONL，**没有说明"为什么没有那张表"**。

**影响**
未来看文档的人（包括我自己）会以为漏实现了一张表。

**修复**
README 明确写出「会话文件是自描述的…因此回看不需要额外的索引表」，把取舍固化进文档。
