## 附 ✅ 提交后暴露的 `snapshot.mjs` 两个真缺陷（D4 验收顺带发现，已修）

D1 决定「提交」之后，快照工具的前提变了。按文档里那条命令复跑 `--verify`，**实测**报红：

```
✓ 已从 HEAD (ca1cdf96) 导出干净树        ← 打印的却是旧 commit
✗ 补丁套用失败：patch does not apply      ← 全部文件
✗ 逐文件哈希一致：81/103
```

看起来像"快照损坏、回滚能力没了"。追下去发现是工具自身两个缺陷：

1. **基线取错**：`git archive HEAD` 用的是**当前** HEAD，而打印文案写的是 `manifest.head`。
   "重构未提交"的年代两者恰好相同，所以一直没露。提交后 HEAD 前进 → 导出了新树去套旧补丁 → 全崩。
   快照的语义是「基线 + 本快照 = 快照时点的工作区」，基线必须取自 `manifest.head`。
2. **空补丁**：只含新增文件的快照 `patchBytes=0`，而 `git apply` 对空文件**报错** → 完好快照被判失败。

同时把判定拆成两级（原先"快照过期"和"快照损坏"混为一谈，都算失败）：

| 判定 | 含义 | 退出码 |
|---|---|---|
| **A. 快照自洽** | `files/` 副本哈希与 manifest 相符 + 补丁能套到记录基线上 | 决定成败 |
| **B. 是否仍与当前工作区一致** | 还原后 vs 当前工作区 | 只告警 |

修完再跑同一份历史快照：**补丁套用成功、自洽 103/103、退出码 0**，
并如实报出"与当前工作区 23/103 不同 —— 它是可用的历史还原点，但不是当前状态的回滚点"。

**阴性对照**（已进 `test-snapshot.mjs`，52 项全绿）：
只 B 不成立 → 退出码必须为 0；A 不成立（副本哈希不符）→ 退出码必须为 1。

> 顺带纠正一个说法：先前那份报告写"要么整体回滚，要么用 snapshot.mjs 的整体快照"。
> 现在**回滚的正规粒度是 git 提交**（分支 `refactor/p0-p6`），快照是补充手段。
