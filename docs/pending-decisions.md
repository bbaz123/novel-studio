## D6 · 删作品后，AI 埋点行怎么办（自审新发现）

| | |
|---|---|
| **现状** | `ai_eval_events` 的 `work_id` / `chapter_id` 是**裸 INTEGER，没有写 `REFERENCES works(id) ON DELETE CASCADE`**（`db.js` 的建表语句），而库里其它二十余张作品域表**全都写了级联**。后果：删掉作品后，它的埋点行留在表里，任何作品视角都够不到；而 `GET /api/ai/eval`（不带 `work_id`）会把它们算进**全局**采纳率与平均编辑距离 → 数字被已不存在的作品带偏。 |
| **实证** | 我自己的验证跑动就留下过 4 行孤儿（在压力库，我已手工清掉）。诊断已固化进 `survey.mjs`：`node .p1-baseline/survey.mjs <库>` 会报「总行数 / 孤儿(作品已删) / 孤儿(章节已删)」，有孤儿时打警告。真库目前**还没有这张表**（P6 未执行）。 |
| **选项** | A. 保持现状（当作长期分析历史）；B. 保留数据，但**全局聚合排除孤儿**；C. 删作品时**连带删埋点**（与其它表一致） |
| **影响** | A：全局指标随删作品而失真，且表无界增长；B：指标诚实、不动历史数据，但孤儿行仍无界增长；C：语义最一致，代价是失去"已删作品的 AI 使用史" |
| **代价** | SQLite **不能给已有表补外键**（`ALTER TABLE` 不支持），所以 C 要落成两条路之一：<br>① 在删作品的 DELETE 分支里**显式删** `ai_eval_events`（最简，无需迁移）；<br>② 重建表迁移（重、且要处理已有数据）。**建议 ①**。B 只改一句 SQL 的 WHERE。 |
| **我的建议** | **C-①**：与库里其它表的约定一致，改动一行 SQL、可回滚、无迁移风险。若你更看重"保留已删作品的 AI 使用史"，则选 B（`summarizeAIEval` 里排除孤儿）。 |
| **需要你回** | A / B / C-① / C-② |
