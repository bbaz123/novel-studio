## 二、第 2 步：实际修改

### 中断前的 4 项（已核实在盘上，未重做、未回滚）

1. **长篇记忆压缩的出场实体判定覆盖完整正文**（`compressStoryMemory`、`agentMemoryGuardOf`）
   改为 `SELECT title, summary, content` + `plainText(完整正文)`。
   旧实现只看头尾各 2000 字，会漏掉长章节中段首次出场的实体 → 该实体不进 `mustKeep` → 压缩摘要可**静默丢掉**它，
   而这段记忆要喂给之后每一章。该读取只发生在显式压缩/护栏路径，不进常规生成上下文。
2. **长篇记忆压缩输入覆盖**（新增 `compactEntityLinesWithinBudget`）

   优先整体覆盖率，不牺牲人物核心信息。
3. **角色卡极端预算截断**（`buildCharacterCards`）
   末级兜底不再 `.slice(0, per)` 切整卡；核心字段（名称/身份/性格/当前状态）全保，
   只截可选长字段（背景/对话示例/system prompt/外貌/标签）；核心本身超预算时保留完整核心并交装配器报 `overflow`。
4. **静态文件路径边界**（`serveStatic`）
   改用 `path.relative(publicDir, filePath)` + `'..'+path.sep` / `isAbsolute` 判断。

### 本轮修复的第 5 项：AI 记忆提案采纳护栏的作用范围

**问题**：中断前的 `settleProposals` 判据是「凡是带 `summary` 的提案一律进 AI 零损失护栏」，
导致第 6 组冒烟测试的 9 字普通提案被「压缩结果过短（<100 字）」拒绝 → `applied.memories` 从 1 变成 0。

**更深一层的真因**：提案表**没有保存来源**。`guard:'agent'` 只在 `PUT` 请求体里活过一次，
`addMemoryProposal` 的 INSERT 没有这一列 —— 来源在落库那一刻就被丢掉，
采纳端**无法**区分「模型自压缩的完整摘要」与「普通/历史提案」。

**修复**（最小、向后兼容）：

- `db.js`：`story_memory_proposals` 新增 `guard TEXT NOT NULL DEFAULT ''`；`MIGRATIONS` 加对应 `ALTER TABLE`。
- `server.js`：`addMemoryProposal` 接收并写入 `guard`；提案分支透传 `body.guard`；
  `settleProposals` 判据改为 `p.guard === AGENT_GUARD_MARKER`（复用既有单一出处常量，不写字面量）。

**链路逐环节实测**（非推断）：
插件 `novel-tools.mjs`（`guard:'agent'`）→ `PUT /api/story_memory` → `addMemoryProposal` 写 `guard` 列 →
`SELECT *` 读回 → `settleProposals` 判定。探针输出：`id=1 guard="agent" summary_len=92 含林晚=true`。

**为什么不会破坏已有提案**：① 采纳行为只在 `guard==='agent'` 时改变；② 列默认空串，旧行天然是普通提案；

### 本轮我造成的错误与修复（强制复盘）

**发现的问题**：用 `(Get-Content -Raw) -replace ... | Set-Content` 做「只改 4 行」的机械替换，
把 `frontend-test.mjs` 的 UTF-8 中文**整文件写坏**（`git diff --stat` 出现 304+/372-，
`node --check` 报语法错，损坏出现在与替换无关的行）。

**修复内容**：① 停止手工修乱码；② **逐字节**定位干净还原源 —— 实测多份 `backup-*` 的同名文件
**都已被后续轮次改过**，只有 `backup-review-v096-*` 的 `git hash-object` 与 `HEAD` **完全相等**；
③ 从该备份还原并用 `git hash-object` 再次确认逐字节一致；④ 用结构化编辑工具重做同一处改动；
⑤ 在本轮备份 README 中写明该陷阱与正确还原方式。

**验证结果**：还原后 `node --check` 通过、`git status` 干净；重做后前端回归 ALL PASS；
`check-utf8.mjs` 报 873 文件 0 处非法 UTF-8；全量套件复跑全绿。

**错误根因**：PS 5.1 的 `Set-Content` 默认按 **ANSI** 写、`Get-Content` 把无 BOM 的 UTF-8 按 **ANSI** 读，
两次错误编码往返写坏整文件。更深一层：**把「文本替换」当成纯 shell 操作，只验证「替换命中了没有」，
没有验证「文件还是原来的编码吗」**；挑还原源时**只凭目录名新旧、没做逐字节校验**。

**以后避免规则**：① 改文件只用带编码保证的工具（编辑工具 / Node 显式 utf8），
**绝不用 PowerShell 文本管道就地改写含非 ASCII 的源码**；② 文本文件改动后立刻跑仓库编码检查器；
③ 还原备份前必须 `git hash-object` 逐字节比对；④ 机械替换后把 `git diff --stat` 的增删行数
与「预期改的那几处」对账，量级不符立即停下排查。

### ① 护栏字数下限随作品规模自适应 —— **已实现（唯一的真实产品行为变更）**

**新语义**（`ai/memory-compress-guard.mjs` 的 `minCharsForStory`）：

```
下限 = clamp( max( 按篇幅分档, 必须保留实体数 × 16 ), 100, 640 )
  按篇幅（正文总字数）：≤5k→100 ｜ ≤2万→150 ｜ ≤5万→220 ｜ ≤10万→300 ｜ ≤20万→400 ｜ ≤40万→520 ｜ >40万→640
```

- 用户规格：**长篇不能仅因实体名称仍存在就判为零损失**，要保证剧情线程、伏笔、
  角色状态有足够承载空间。名称检查只回答"人还在不在"，回答不了"事还记不记得"。
- `MAX_COMPRESSED_MIN_CHARS = 640`：**刻意不超过下游提示词"不超过 800 字"的产出目标**
  —— 下限高于产出目标会要求模型写一个它被明确告知不要写到的长度（成对契约）。
- 两个量取 **max 而不是相加**：第一版写成 `100 + n×16`，实测把 134 字的正常摘要判成过短
  （判据过紧同样是缺陷）。极端规模下封顶 640，不再继续抬高。
- **实测档位**：work#2（7141 字/6 出场）→150；23 个实体 →368；压力库（18.4 万字/50 实体）→640。
- **接线**：`compressStoryMemory` 传 `storyChars: chapterChars`（从已读入的章节行求和，不额外查库）；
  `agentMemoryGuardOf` 同样传规模（实测该路径整条 ~8.7 ms）。
- **测试**：`test-memory-compress-guard.mjs` **65/65**（新增第 11 节：分档单调、封顶、配对契约、
  "长篇里实体齐全但 136 字 → 被拒"）；`test-agent-memory-guard.mjs` **47/47**（新增 5b 节）；
  插件冒烟新增"长篇规模下实体齐全但字数不够 → 409"端到端断言，**39/39**。
- ⚠️ 按用户要求**没有为兼容旧的 100～138 字夹具保留旧行为**：smoke 的"合格摘要"夹具改为
  `repeat(28)`（≈644 字 > 640），并注明"取值范围随作品规模变，夹具必须按当时的下限算"。

### 本轮我造成的第二个错误（已完成复盘）

**问题**：刷新 `.p1-baseline/data/` 基线副本时，我对**真实库**执行了
`PRAGMA wal_checkpoint(TRUNCATE)` 并直接复制文件（两处都超出必要范围：我只是想消除
"真实库未被写入"那条检查的过期差集），结果副本变成 `database disk image is malformed`。

**修复**：确认真实库 `integrity_check = ok` 且数据完好（2 作品/7 章/9529 字/guard 列在）→
从真实库重新复制副本 → **SHA-256 与 integrity_check 双验证一致**。
真实库从未受损；副本目录在 `.gitignore` 内，不影响仓库。

**根因**：把一个"只需读"的维护动作做成了"写 + 裸文件复制"——真实库当时刚被实例写过，
我却**没有先确认写入是否停止、也没在复制后做完整性校验**，直接把"复制成功"当成"副本可用"。

**以后规则**：① 复制 SQLite 前先确认**没有进程在写**（或确认无 WAL），复制后**必须**跑
`PRAGMA integrity_check` 与哈希对账；② 能只读解决的（如差集归因）**绝不写库**，
尤其不要对真实库做 checkpoint 之类会改动文件的维护操作；③ 副本损坏先查真实库完整性，
再决定是否重建，不要先去修副本。
