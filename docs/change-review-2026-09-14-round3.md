## 发现的失误

| # | 严重度 | 失误 | 后果 | 修复 |
|---|---|---|---|---|
| 1 | P2 | **同类病灶只修了一半**：第二轮修了 `runHarnessJob` 的「互斥检查与置位之间隔着 await」竞态窗口，但 `resumeHarnessJob` 有完全相同的窗口（检查与置位之间隔着 `/harness/recovered` 的 GET）；且第二轮把置位提前后，其提前 return 路径（GET 失败 / 任务不可续接）不在 finally 保护内 → 锁泄漏 | 两次快速点击可同时穿过互斥检查；GET 失败后锁永久不释放 | `resumeHarnessJob` 检查后立即置位，整体 try/finally 无条件释放，覆盖所有提前 return |
| 2 | P2 | **标记与展示不同步**：mark_applied 只写服务端（kind 后缀），前端 `state.chapterJobs` 本地缓存不更新 | 恢复条继续挂着「已完成，结果待应用」，直到下次切章重取——用户看到的界面和修复前一样 | 新增中央 helper `markJobApplied(jobId)`＝服务端 POST + 本地移除 + 恢复条立即重绘，所有交付点（成文弹窗 / 审稿报告 / 修稿差异 / 取回路径）统一走它 |
| 3 | P3 | **模式分支静默 no-op**：取回成文结果的路径里，结果弹窗返回的 mode 只有 insert/replace/append 有处理，'regenerate' 与 null（用户取消）落到 `applyAIWritingArticle` 是静默 no-op | 用户点「重新生成」/「取消」没有任何反应 | null → 直接返回；'regenerate' → 明确 toast「本版已存草稿，请从 AI 写作重新发起」 |

## 根因

1. 修复「模式级 bug」（竞态/泄漏/口径不一致）时只盯着报错点，没有 grep 全仓同类结构——`grep aiTaskRunning` 就能列出全部「检查-置位」对，却只改了一处。
2. 把「数据侧标记」当成了「完整修复」，忘了前端还有一份缓存副本要同步。
3. 调用带 mode 参数的函数前，没有先枚举该参数的全部可能取值，确认每个取值都有行为或显式忽略。

## 新增防复发规则

- 修任何「模式级 bug」必须 grep 全仓同类结构，一次修完；只修报错点 = 下次一定再犯。
- 状态标记必须「写 + 展示」成对：任何数据侧的状态变更，都要问「展示侧读的是谁、什么时候刷新」。
- 任何带「模式/分支」参数的调用点，写完后把参数的所有取值枚举一遍，逐一确认有行为或显式忽略，禁止静默吞掉。

重审的价值正在于「修复的修复」：第二轮 8 处修复里，有 2 处（竞态窗口、标记不同步）本身就是上一轮病灶的同类复发。**修复动作必须附带"同类排查"，否则重审会变成无限循环。**
