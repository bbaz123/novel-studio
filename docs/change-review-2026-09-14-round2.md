## 已修复的失误

| # | 严重度 | 失误 | 后果 | 修复 |
|---|---|---|---|---|
| 1 | **P1** | 「接回进度」调用 `pollHarnessJob` 后**不释放互斥锁** `state.aiTaskRunning`（释放只在 `runHarnessJob` 的 finally 里） | 一次接回（无论成败）后，所有 AI 任务被「已有任务进行中」永久锁死，直到刷新页面 | `resumeHarnessJob` 用 try/finally 无条件释放；`runHarnessJob` 的置位提前到互斥检查之后，堵住「检查与置位间隔一个 await」的竞态窗口 |
| 2 | **P1** | 蓝图确认校验 `Object.values(bp).some(...)` 混入 `target_words`（默认 2000，**恒为真**） | 六个文本字段全空也能通过校验——想堵的「空蓝图照样成文」口子实际没堵住 | 只校验六个文本字段 |
| 3 | P2 | `resumable: !!live`（「还在内存」≠「还在运行」） | 已完成/已失败任务在恢复条显示「接回进度」按钮 | `resumable = live && status in (queued, running)` |
| 4 | P2 | 只写「标记已应用」不写「过滤已应用」 | 恢复条永远挂着「已完成，结果待应用」 | 新增 `POST /harness/mark_applied`；成文弹窗打开 / 审稿报告展示 / 修稿差异预览三个交付点统一标记；列表 SQL `kind NOT LIKE '%:applied'` |
| 5 | P2 | SSE `onerror` 先 `close()` 再按 readyState 分叉「交给浏览器自动重试」 | 连接已被自己关掉，浏览器不会重试 → 录制中实时流永久死亡 | 重连策略唯一化：始终自己 3 秒重连 |
| 6 | P2 | `sessionSummary`/`traceState` 用累加计数器 `op.errors`，与 `opSummary` 的「按节点事实重算」口径不一致 | 收尾后补挂的 error 节点在会话级统计里隐身（与当天「19 次崩溃只报 2」同源） | 统一 `opErrorsOf(op) = max(计数器, 节点事实)`，三个出口同源 |
| 7 | P3 | 取回成文结果先 `finalize` 存草稿、结果弹窗又存一份草稿 | 同一内容两份草稿记录 | 删除 finalize 路径的重复落库，草稿只由结果弹窗落 |
| 8 | P3/P4 | `harness_jobs` 表无上限；审稿 GET 返回 200KB 原文；恢复条引用未定义的 `.recovery-*` 样式；时钟自检日志把负天数当正数 | 存储/带宽/样式/日志小问题 | LIMIT 100 裁剪；raw_text 截 20KB；补样式；`Math.abs` |

## 根因（为什么这些错会发生）

1. **抽取公共函数只搬「获取」没搬「释放」**：`pollHarnessJob` 承担了置位义务，释放却在 `runHarnessJob` 的 finally；新调用点不知道有这份义务。
2. **校验条件混入恒真默认值**：写校验时没枚举每个参与值的可能取值。
3. **布尔标志语义与字段名没逐字核对**：`!!live` 在三种状态下都不是字段名的意思。
4. **状态标记与过滤条件没成对设计**：只写标记不排除查询，等于没标记。
5. **重连策略分叉后没走一遍分支**：`close()` 之后「交给浏览器」根本不会发生。
6. **同一个量的口径没统一推广**：`opSummary` 改成按事实重算后，没把结论推广到其余两个出口。

## 元教训

- 重审必须假设「自己上一轮一定有错」：8 处里 4 处是「写了但不会生效」形态（短路/泄漏/死路/未配对），happy path 测试全绿也发现不了；重审要专门找"看似在做事、实际被旁路"的代码。
- 新功能的验证要覆盖负路径：接回失败、SSE 断开、校验拦截、标记后再查询——负路径比正路径更容易藏 bug。
