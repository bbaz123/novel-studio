# 成文时间全方位缩短 · 方案（口径 A 机器时间 + 口径 B 交付时间）

> 本文是**方案**，不是验收报告。所有"现状"数字都来自**真实库与真实代码**（出处逐条给出），
> 所有"预期收益"都明确标注为**估算**——没有实测过的收益不写进结论。
>
> 最高约束：**任何一条优化都不得以牺牲小说生成质量为代价**。
> 不改模型、不降 reasoning effort、不砍上下文、不跳质检、不并行拼章。

---

## 0. 一页结论

1. **冷启动不是肥肉。** 生产路径的冷启动实测 1844ms，只占一次直连成文（30–42s）的约 2%。
   把冷启动优化到 0 也换不回几秒——所以它不是本方案的主线，排在最后（P2-4）。
2. **真正的三处肥肉，按可回收的绝对时间排序：**

   | 排序 | 问题 | 可回收的时间 | 依据 |
   |---|---|---|---|
   | ① | **空回复把整轮烧掉**：思考 token 吃光 `max_tokens` → 正文 0 字 → 重试又烧一轮 → 最后回退慢通道 | 一次事故 **1–2 分钟（直连重试）+ 2–6 分钟（慢通道）** | 真实库 7 次空回复，其中 2026-09-21 连续两次（1500 → 8192 上限全被思考吃光）后回退慢通道 —— **P0-1 已落地**，见 §3 |
   | ② | **不必要的慢通道轮次**：每一轮比直连贵 5–10 倍（含 ≈17s 固定开销 + 轮询发现延迟） | 每轮 **约 17s 固定开销 + 1.5–10s 发现延迟** | 慢通道任务 46 条实测：中位 65s、p90 169s；同一条蓝图提示词 直连 19.1s vs 慢通道 47.3s |
   | ③ | **可合并的轮次**：蓝图 / 成文 / 补足各自重放 1.3–1.5 万字上下文 | 每省一轮 **19–42s** | 每轮 `chars_in` 实测 12905 / 14941 |

3. **顺序必须是"先测量 → 再动手"**：本方案的 P0-4（埋点补真）**已落地**，
   因为在此之前 `ai_eval_events` 的 `ms` 恒为 0、`channel`/`model` 恒为空串（真实库 4 行全部如此），
   "提速有没有生效"**根本无法被证明**。
4. **P0 三条不改一个字的生产 prompt、不降任何模型能力**，是对质量**零风险**的纯工程修复。
   P1 起会碰 prompt 结构与上下文顺序，**必须先做 A/B 对照**才允许保留。
5. **当前进度（2026-09-25）**：**P0 全部收口** —— P0-4（测量基座）✅、P0-1（空回复 + 思考余量 +
   "正在思考"相位）✅、P0-2 前置（流式用量回传，P1-3 的判据）✅、
   P0-2 主体（算账后改成"轮询上限 10s→3s"，回收约 3.5s/轮，**不新增推送端点**）✅、
   P0-3（取消/超时不再丢已生成的正文）✅。
   仍待做：P1 四项（全部需要 A/B 质量对照）、P2 四项（结构性/并行）。
6. **⚠️ 生效前提**：本轮新增的 `cached_tokens` / `reasoning_tokens` / 思考相位都要**重启服务端**才生效
   （`server.js` 的改动不像 `public/app.js` 那样刷新页面即可）。在重启之前，不要把"查不到缓存命中"
   当成"前缀缓存真的没命中"——那只是还没测到。

## 1. 两个口径（必须分开报，混在一起会得出错误结论）

| 口径 | 定义 | 从哪里读 | 它回答的问题 |
|---|---|---|---|
| **A 机器时间** | 点「AI 写本章」→ **草稿出现在结果弹窗** | `app_logs` 的 `kind:ai_write_timing`（`total_ms` + `phases[]`）与 `ai_eval_events.ms` | 机器快不快？慢在哪一轮？ |
| **B 交付时间** | 点「AI 写本章」→ **作者点「应用到正文」采纳** | `ai_eval_events` 里**同 `draft_key`** 的 `adopt.created_at − generate.created_at` | 作者多久真正拿到能用的稿子？ |

**为什么必须分开**：一次 A 只有 40s、但作者看了三分钟又点了「重新生成」，B 就是 3 分钟 + 第二次 A。
只盯 A 会得出"已经很快了、不用改"的结论；只盯 B 会把"作者在犹豫"错当成"机器慢"。

B 口径**不需要新增测量代码**：`generate` 与 `adopt` 两行本来就共用 `draft_key`，
两个 `created_at` 相减即得。返工量已有 `edit_distance`（采纳后作者又改了多少字）在测。

## 3. 优化清单

### P0 · 零质量风险（不碰 prompt / 模型 / 上下文）

**P0-1 ✅ 已落地（2026-09-25）：让额度覆盖「思考 + 正文」，并把重试阶梯拉回纪律**

先测量（真实库 + 真实日志）：
- `ai_direct_empty` 共 **7 次**，**全部**来自**非流式**路径；成文流式路径
  （`ai_write_stream_empty_retry`）**0 次** → 成文轮的额度本来就够，问题在非流式调用。
- 2026-09-21 同一天两条完整失败链，每次都是：**1500 被思考吃光 → 8192 又被吃光 →
  换 low 强度 + 8192 还是被吃光 → 回退精写内核**。而 1500 正是"gap≈250 字的小缺口补足"
  按 `gap*2+1000` 算出来的额度 —— 它只算了正文，没算思考。

改了什么（`public/app.js`；只动额度参数、重试顺序与日志，**不动 prompt / 模型 / 上下文 / 思考强度上限**）：
1. **`withThinkingHeadroom(额度)`**：非流式的"按正文长度定额度"的调用（小缺口补足 ×2、质检轮、提问轮）
   统一改成"正文额度 **+ 思考余量 8192**"，封顶 16384。8192 不是拍脑袋——它就是实测里被思考吃光的量。
2. **重试阶梯对齐纪律**：`directAIWrite` 此前在预算被吃光时**跳过**"保持原思考强度"的那次重试、直接降到 low；
   而该函数头注释写的一直是"放宽输出上限再试一次；只有仍为空时才降思考预算兜底"——实现与自己的描述自相矛盾。
   现在一律 **① 原强度 → ② 原强度 + 更大上限 → ③ low + 更大上限**，与成文流式路径同一条纪律。
   该改动**只在上一轮产出 0 字时才触发**，因此不可能降低任何一次成功生成的正文质量。
3. **失败阶梯留痕**：新增 `app_logs` `kind:ai_empty_ladder`，把每次尝试的额度 / 结束原因 / 思考 token 一次记全。
   此前 7 条日志各自为政，其中 2026-09-14 那两条 `context` 是空的，事后无法归因。

顺带修掉的**静默降级**：质检轮的额度此前也是 1500——思考一吃光就返回空，而空回复在 `verifyAIDraft` 里
**等价于"质检静默跳过"**（`skipped` 分支），质量门会无声消失。现在额度覆盖思考，这道门能真的跑起来。

证据：`frontend-test.mjs` 新增 113a–113g 七条断言（**既有期望值一字未改**），并做**变异对照**——
把上述三处分别改回旧写法，6 条断言精确报红（其余全绿），证明断言承重、不是恒绿。

**✅ 已落地（2026-09-25）：服务端 SSE 附加"正在思考"信号 + 进度卡提示**

DeepSeek 的思考以 `delta.reasoning_content` 逐片下发，**正文之前可能持续十几秒**；而这些帧此前被整个
忽略 —— 客户端在这段时间里一帧都收不到，进度卡上一直写着"已 0 字"，作者看到的与一个卡死的界面
完全一样。而作者一旦以为卡死，就会点「停止」或「重新生成」——**口径 B 直接变差**，所以这条不是"好看"。

改法（`server.js` + `public/app.js`，纯附加）：
- `doStream` 在第一个 `delta.reasoning_content` 出现时回调 `options.onThinking()`，**每个流只报一次**；
  `handleAIWriteStream` 把它作为 `{ phase: 'thinking' }` 随流下发。**不转发思考内容本身**
  （不外泄推理过程，也不增加传输量）。
- 客户端收到 `phase === 'thinking'` 就把进度卡换成「AI 写作（2/3 成文）· 模型正在思考…」；
  正文一开始输出就照旧回到「正在生成正文（已 N 字）」。

证据：`api-test-suite.mjs` I5d/I5e（本地假 SSE 端点**真实走** `/api/ai/write_stream`，断言相位排在正文
之前、只报一次、思考内容不混进正文）；`frontend-test.mjs` 116a–116d（含兼容性反向断言：老服务端不发
相位时不误报"正在思考"）。变异对照：把服务端两处接线改回旧写法 → 前端 116d 与接口 I5d 各精确报红 1 条。

**顺带说明**：`ttft_ms`（首字延迟）本来就等于"思考了多久"，所以这次没有新增测量字段 —— 相位只是把
已经花钱买到的信息显示出来。

**P0-2 前置 ✅ 已落地（2026-09-25）：把流式用量回传出来（P1-3 的判据也靠它）**

先测量（真实代码）：`server.js` 的 `callAIStream` 早就把流式最后一帧的 `usage` 收进了 `streamUsage`
（`server.js:834/880`），却**从来没有向外传过**。于是两个直接决定成文耗时的问题一直只能靠猜：
① **前缀缓存命不命中**（`prompt_cache_hit_tokens`——长上下文的重复发送是成文时间的大头）；
② **思考吃掉多少输出预算**（`reasoning_tokens`——空回复事故的根因，见 P0-1）。

改了什么（**纯附加字段**，老客户端与旧服务端互相忽略即可）：

| 位置 | 改动 |
|---|---|
| `server.js` `doStream` | 收尾时把 `streamUsage` 交给 `options.onUsage` |
| `server.js` `handleAIWriteStream` | 注册回调，并把 `usage` 随 `done` 帧下发 |
| `public/app.js` `streamAIDirectWrite` | `done` 帧的 `usage` 透传到返回值（**老服务端没有就记 null，不编造**） |
| `public/app.js` 成文轮账本 | `prompt_tokens / cached_tokens / completion_tokens / reasoning_tokens` 展开进 `phases[]` |
| `public/app.js` `directAIWrite` | 非流式留痕补上输入侧两项（`prompt_tokens` / `cached_tokens`） |

证据：`frontend-test.mjs` 114a–114e（含"旧服务端必须记 null"的阴性对照）；
`api-test-suite.mjs` I5a–I5c 用本地假 SSE 端点**真实走** `/api/ai/write_stream`，
断言 `done` 帧确实带上缓存命中与思考 token。变异对照：把三处服务端接线改回旧写法 →
前端 114c 与接口 I5b 各精确报红 1 条（其余全绿）。

怎么查（本轮起才有数）：
```sql
SELECT json_extract(context,'$.phases'), created_at
FROM app_logs WHERE kind='ai_write_timing' ORDER BY id DESC LIMIT 20;
-- name='prose' 的那一项会带 cached_tokens / reasoning_tokens / prompt_tokens
```

**P0-2 主体 ✅ 已用更小的手段覆盖（2026-09-25）—— 结论是"不新增推送端点"**

先算账（这一步决定了要不要动手）：

| 事实 | 出处 |
|---|---|
| 发现延迟 ≈ 下一个轮询时刻 − 任务真正完成的时刻，**上界就是轮询间隔上限**，与任务时长无关 | `public/app.js` `pollHarnessJob` 的退避循环 |
| 10s 上限下，中位 65s 的任务平均晚 **4.5–5s** 才被发现；p90 169s、max 567s 也是同一个绝对差（间隔早已触顶） | 按同一段退避逐次累加推算 |
| 每次轮询回包最多 **600 字**（`job.tail.slice(-600)`），服务端只读**内存任务表**、不碰数据库 | `server.js:4984` |
| 进度"像卡死"这一半**本来就不成立**：轮询已经在用 `job.tail` 刷进度卡 | `pollHarnessJob` 里的 `progress.update` |

于是改法从"新增 SSE 端点"换成"把轮询上限从 10s 收到 3s"：
- 回收 **约 3.5s/轮**（均值 5s → 约 1.5s）；而新增推送端点只再多回收约 **1.5s/轮**，
  却要引入断线重连语义与双路径兼容 —— 按"质量优先 > 稳定性 > 性能"，不值得。
- 代价：请求数 ×3。在本机是免费的（见上表第 3 行）。
- 回退：把 `Math.min(3000, …)` 改回 `10000`，没有任何其它耦合。

证据：`frontend-test.mjs` 117a/117b —— 用"记录间隔 + 立即执行"的 `setTimeout` 替身精确观察轮询节奏，
断言上限为 3000、首个间隔仍为 1500，且任务完成后照常返回产出。变异对照：把 3000 改回 10000 →
117a 精确报红（`[1500,2500,3500,4500,…]`），117b 仍绿。

**P0-3 ✅ 已落地（2026-09-25）：取消 / 超时不再销毁已生成的正文**

先测量（真实代码路径）：成文轮流式直连的三条中断出口（点「停止」、连接中断、读取异常）此前都把
已经收到的正文**连同进度卡一起丢掉**——错误文案自己就写着"白等"。更隐蔽的一层：成文流一失败就
回退慢通道**从头重新生成**（质量优先下的正确选择），于是那段正文会随着被替换掉的错误一起消失。

改了什么（`public/app.js`；只搬运文本、只多写一行草稿，**不改任何生成行为**）：
1. `streamAIDirectWrite` 逐字记录已收到的正文，并在每条中断出口把它绑到抛出的错误上
   （`err.partialText`）。**仍然抛错、仍然不把残缺正文当成品返回**——「不当作成品交付」是质量纪律，
   「就地销毁」只是白白扔掉作者的等待，两者不是一回事。
2. 管线层新增 `interruptedPartial`：成文流回退慢通道前先接住这段正文，避免它随错误被替换而丢失。
3. 管线最终失败时调用 `saveInterruptedDraft()`：**只保存、不应用**（正文永远由作者自己决定要不要写回），
   并如实告诉作者去哪里取——「已取消 AI 写作；已生成的 N 字已存为草稿，可在章节里「取回生成稿」」。
   断流/超时路径同样处理，错误弹窗里多一行说明（弹窗本身、原因文案都照旧）。
4. 门槛 `MIN_SALVAGE_CHARS = 200`：碎片段不落草稿。理由是 `getLatestDraft` 只取最新一份草稿，
   一次误点「停止」不该把上一份好稿从「取回生成稿」里顶掉。

收益（口径 B）：把"白等 2–6 分钟、手里什么都没有"变成"至少拿得回已经写出来的部分"。
质量影响：零（不自动应用、不改 prompt、不改额度、不改通道）。

证据：`frontend-test.mjs` 115a–115e，其中两条是**反向**断言——碎片不落草稿（115d）、
取消仍然不弹错误框（115c）。变异对照两个方向都做了：① 去掉门槛 → 只有 115d 报红；
② 去掉两处落草稿调用 → 恰好 115a/115b/115e 三条报红（115c/115d 仍绿）。

**仍未做（列为 P2，需先证明必要）**：生成过程中的周期性落盘。它多覆盖"浏览器崩溃 / 关标签页 /
机器休眠"这几类更罕见的损失，代价是要在生成热路径上周期性写库——**先证明收益大于风险再动**。

### P1 · 需要 A/B 质量对照（会动 prompt 结构与上下文顺序）

**P1-1 减轮次：跳过提问时把"蓝图 + 成文"合成一轮**
- 交互路径上作者点"不要再提问"后，当前仍要多跑一轮蓝图；合并可省一轮 ≈19–42s。
- 风险：合并后模型要一次完成"规划 + 写作"，**可能降低成文质量** → 必须 A/B，且默认保守。

**P1-2 补足改成同一流内续写**
- 现状：字数不足时**重开一轮**，重放 1.3–1.5 万字上下文。
- 改法：在同一条流里续写（上下文已在 KV 里），省掉重复 prefill 与重新思考。
- 风险：续写点的衔接质量 → A/B + 人工抽检。

**P1-3 前缀缓存友好化**
- 现状：系统提示词 + 上下文 + 变量混在一起，每轮前缀不稳定 → 供应商侧的上下文缓存命中不了。
- 改法：**内容不变、只调顺序**——稳定前缀（系统提示 + 上下文层）逐字节固定，把【本章蓝图】等变量挪到末尾。
- 前置动作（零成本）：先从 `usage` 取 `prompt_cache_hit_tokens`，**先证明现在确实没命中**再动手。
- 风险：这是 prompt 结构调整，**必须 A/B**；顺序本身可能影响模型注意力，不能假定"等价"。

**P1-4 确定性预检前置**
- 把章节边界/未登记实体等**本地可判定**的检查从"生成后质检"提前到"生成前写进提示词"，
  减少"生成完才发现要重写"的整轮浪费。

### P2 · 结构性 / 并行

| 项 | 内容 | 前置条件 |
|---|---|---|
| P2-1 | 批量生成并发（当前 2）适量提高 | 受模型限流约束，需实测失败率；抢不到槽位会 429 静默丢提案 |
| P2-2 | 章间流水线预取（写第 N 章时后台准备 N+1 章上下文/蓝图） | 要有并发与取消的隔离保证 |
| P2-3 | 直连/慢通道路由复核（哪些轮真的需要工具循环） | 不搞"全部直连"也不搞"全部慢通道"，按"是否需要工具/多步状态/强一致"决定 |
| P2-4 | 热备池 `ai/harness-pool.mjs`（已实现、**未接线**） | 冷启动只占约 2%，**排在最后**；接线属产品决策 |

## 4. 本轮已落地：P0-4 埋点补真（口径 A / B 从此可测量）

**为什么它是前提**：真实库里 `ai_eval_events` 共 4 行，`ms` **全部为 0**、`channel`/`model` **全部为空串**——
因为三处 `showAIWritingResult` 调用从来没有把 `meta.channel/model/ms` 传进来过。
在这种状态下，任何"提速"都无法被证明，也无法被证伪。

**改了什么（`public/app.js`，纯附加式）**

| 位置 | 改动 |
|---|---|
| `newWriteTiming()`（新增） | 分轮耗时账本：`round(name, ms, {via, ttft_ms, chars…})` → `summary()` 给出 `total_ms / ttft_ms / rounds / direct_ms / harness_ms / phases[]`。全部是 `Date.now()` 差值，**不参与任何决策**，异常内部吞掉 |
| 蓝图轮 / 成文轮 / 质检返工 / 补足轮 | 每轮记 `via`（**实际**用到的通道）、耗时；成文轮额外记 TTFT 与字数 |
| `streamAIDirectWrite` | 新增 `ttftMs`（首个**正文** delta 的时刻）与 `ms`（含重试的墙钟）。服务端下发的 `delta` 是 `choices[0].delta.content`，**不含 reasoning**，所以这个数字就是"思考结束、开始写正文" |
| `runHarnessJob` | 新增客户端观测 `ms`（入队 + 轮询 + 执行）；减掉服务端 `duration_ms` 即得轮询净开销 |
| `showAIWritingResult` | 把真实 `channel/model/ms` 写进 `ai_eval_events`；并**附加**一条 `app_logs` `kind:ai_write_timing`（含分轮明细与 `draft_key`） |

**怎么查（口径 A）**
```sql
SELECT json_extract(context,'$.total_ms'), json_extract(context,'$.ttft_ms'),
       json_extract(context,'$.direct_ms'), json_extract(context,'$.harness_ms'),
       json_extract(context,'$.phases'), created_at
FROM app_logs WHERE kind='ai_write_timing' ORDER BY id DESC LIMIT 20;
```

**怎么查（口径 B：交付时间 = 两行时间之差）**
```sql
SELECT g.draft_key,
       ROUND((julianday(a.created_at)-julianday(g.created_at))*86400.0) AS deliver_secs,
       g.channel, g.ms AS machine_ms, g.chars_in, g.chars_out, a.edit_distance
FROM ai_eval_events g
JOIN ai_eval_events a ON a.draft_key = g.draft_key AND a.action = 'adopt'
WHERE g.action = 'generate' ORDER BY g.id DESC LIMIT 20;
```

**为什么用 `app_logs` 而不是给 `ai_eval_events` 加列**：加列要走 schema migration 并触碰已冻结的
Host Contract 表清单（35 张 / 25 张冻结）；`app_logs.context` 本来就是 JSON 观测字段，
**零 schema 变更、零契约变更、零迁移**，符合"最小行为变更 + 可逆"。`ms`/`channel`/`model`
三个**已存在**的列则顺带修好——那不是新增行为，是修一个从未生效的既有字段。

**回滚**：删掉 `newWriteTiming` 与四处 `timing.round(...)` 调用、把三处 `showAIWritingResult`
的 `meta` 还原为 `{ chapterId }` 即可；所有新增字段都是附加式，没有任何代码读取它们。

**行为证明**（`frontend-test.mjs` 新增断言，未改动任何既有期望值）：
- `108h` 结果弹窗拿到真实的通道/模型与分轮账本（此前是空串与 0）；
- `112a/112b/112c` 埋点**落库请求**里就是真值：`channel/model/chars_in`、分轮明细与 `draft_key`
  在 `generate` 与 `adopt` 两行之间一致（口径 B 可直接算）。

**已知缺口（下一步补）**：批量生成路径（`batchGenerateChapters`）只记到"每章墙钟耗时"，
**还没有分轮明细**；它用的是另一套内联流程，需要单独接线。

## 5. 质量红线（不做）

- 降模型档位、降 reasoning effort、关思考换速度；
- 砍上下文层、缩短长期记忆、少放角色卡/世界观；
- 跳质检轮、跳红线扫描、跳一致性核对；
- 把一章拆成并行分段再拼接；
- 把慢通道整体替换成直连（会丢工具循环与入账链路）；
- 未证明用户无感就改动默认路由/默认预算。

1. **口径 A 前后对照**：同一作品、同一章、同一模型、同一核心设置，`ai_write_timing` 的分轮数字；
