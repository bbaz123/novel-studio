## 0. 结论先行

方案要求的**架构在 v1.2.4 已经落地**：`finding.v2` 逐字证据与角色、多热点授权、补丁协议 v2
与门禁、`revision-semantic-verifier` 两层验收、`revision-finalize` 单段/分段统一出口、
`revision-closure` 分离"补丁数 ≠ 修复数 ≠ 已入库"、`review-workspace` 独立工作区。

本轮不是"再实现一遍"，而是在现有实现上补齐**会让"部分修复消失"的四处缺口**，并用作者这次的
I01–I08 样本把"6 修复 / 1 部分 / 1 未修"钉成离线回归：

| 缺口 | 症状（本机探针实测） | 处置 |
| --- | --- | --- |
| **G1** 语义层 `partial` 没被建模 | 模型判"部分修复"时落成 `AWAITING_SEMANTIC` / `SEMANTIC_NOT_RUN`，部分修复这一事实丢失；复验额度已消耗，作者再点被拒 → 该项永远停在待验 | 新增 `partial`（及 `unverified`/`blocked`）裁决、终态与原因码 |
| **G2** `PARTIAL` 不进复修队列 | `planAutoRepair` 只认 `fail/UNRESOLVED` → `NO_TARGETS`；同模块 `repairTargets` 却接纳 PARTIAL，口径不一致 | 统一"可复修"口径；硬阻塞仍排除 |
| **G3** 没有结构化追踪 | 方案 §4.2 的 `revision-trace.v1` 在本机不存在（无文件、finalize 不产出）→ 事后无法回答"第 3 项停在哪道关口" | 新增 `public/revision-trace.js` 并接进运行记录/回执 |
| **G4** 无法机器区分"完全未修改"与"改了但仍有问题" | 终审行没有 `actual_change`，只有 `ANCHOR_NOT_EDITED` 一个粗粒度原因 | 终审行补 `actual_change` / `patch_ids` / `evidence_ids` / `remaining_evidence` |
| **G5**（实现中发现的真实缺陷）复修会冲掉旧结论 | `runRevisionAutoRepair` 复修后用确定性重验结果替换上一轮语义结论，会把已 PASS 的 6 条打回 `AWAITING_SEMANTIC`；复修后复验只按 `unresolved>0` 触发，部分修复不触发 → 复修后反而"全部待验" | 新增纯函数 `mergeRepairSemantic`：未改条目保留结论、改过条目明确待复验；复修后复验按"未通过或待复验"触发，并受剩余预算门禁 |

> 已确认**正确、未改动**的行为：未跑语义时绝不 PASS；锚点原句仍在时模型谎称 pass 仍判
> `ANCHOR_NOT_EDITED`；硬失败不会被语义 pass 覆盖；作者未合并 = 候选态。

**根因边界（如实说明）**：方案 F-08 指出没有本次真实 UI 请求/日志，因此"用户那次到底停在

按当前实现，I04 这类"模型判 partial"的结果会被降级成待验并失去复修路径——与用户观察到的
"1 项部分修复、1 项未修"完全一致。用离线 fixture 能稳定复现并在修复后稳定给出正确结论。
