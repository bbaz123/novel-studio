### 1.1 两个"顺手必须修"的真实缺陷（由新增测试发现）

1. **`tryApplyRevisionOutput` 丢掉了协议字段**：它把 `applied` 映射成 `{issue, anchor, revised}`，
   用 `Number(issue_ids[0])` 取编号（非数字编号如 `B03` → `0`），并**删掉了** `issue_ids` / `original` /
   `replacement`。后果：逐条验收器"候选能否由补丁逐字重建"必然判 `BASE_STALE`，
   闭环里每条 issue 的 `patch_count` 恒为 0 —— 也就是"应用了 5 个补丁"被读成"一条也没改"。
   现在同时保留兼容字段与协议字段。
2. **`revisionFindingsFor` 丢掉无证据条目的 `acceptance`**：像"缺纪年锚点""篇幅不足"这类
   **证据天然不在正文里**的问题，之前会被降级成 legacy finding，`must_contain` / `min_chars`
   在进入验收器之前就消失了 —— 硬约束退化成"模型说什么就是什么"。

这两条都不是"新功能"，而是**把既有闭环接通**。没有它们，P0C/P0D 只是新增文件。

## 2. 判据：什么叫"修好了"

```
作者勾选 8 项
   │
编译授权跨度（Host）→ 局部补丁 → 安全门禁/组合核验
   │
finalizeRevisionCandidate()                ← 唯一出口（单段/分段都走这里）
   ├─ 候选能否由补丁逐字重建？（分段：逐片重建 + 合并保真）
   ├─ 逐条终审：硬事实 / 软判断 / 语义层
   └─ 语义覆盖完备性 semanticCoverageComplete()
         ├─ 有 not_run → AWAITING_SEMANTIC（待复验，不算通过）
         ├─ 有硬事实失败 → UNRESOLVED + 明确 reason_code
         ├─ 有蓝图/词条冲突 → CANON_CONFLICT（待作者裁决）
         └─ 全部通过 → VERIFIED_CANDIDATE（候选，不是已入库）
                              │
                        作者点合并 → PERSISTED_VERIFIED（写回 + 版本一致）
```

**硬事实**（模型说 `pass` 也不能覆盖）：可编辑锚点原句仍在、只读证据丢失、必须保留项被删、
`must_contain` 字面缺失、`min_chars` 硬目标未达、声称改了却无 diff、越过授权跨度、底稿已变。

**软判断**（与语义层冲突时交人复核）：模板句是否仍有伤害、群众反应是否只是"模式化"、
篇幅偏差是否可接受。

### 7.4 本轮修掉的两个真实缺陷（由新测试发现）

1. **`GET /novel/revision/closure/status` 把 `contract_version` 写死成 2**，而回执已是 v3 ——

   永远不相等，于是"候选已验证"会一直被当成"等待修复"。改为优先 `stage`，并把
   `semantic_coverage_complete === false` 判为待复验。

## 8. 作者授权的一次例外 + 复验可见性（2026-10-18 晚）

作者实际点开工作区提出两件事：**要一个"跳过复验直接合并"的入口，并把跳过的后果写在悬停里**；
以及**点了"运行独立语义复验"之后，除了按钮点不动，看不出后台在跑**。两件都按作者原意落地。

### 8.1 新增：跳过复验直接合并（次按钮，不是默认路径）

| 维度 | 做法 |
|---|---|
| 入口 | `AWAITING_SEMANTIC` 档位多一个 **次按钮**（`danger` 样式）「跳过复验直接合并」；复验进行中与已复验过一次时都不出现 |
| 后果说明 | 悬停 / Tab 聚焦即出（`data-help="review_merge_forced"`，走现成的 `.tooltip` 通道，z-index 400） |
| 文案唯一来源 | `review-workspace.forcedMergeWarning()`：① 没有任何逐条结论；② 整章替换正文、旧稿进历史版本可回退；③ 合并后这份候选**不能再复验** |
| 合并路径 | 与普通合并**同一条**（`/novel/adopt` 单事务 + 旧稿进历史版本），差别只在"没有逐条结论" |
| 合并后的档位 | 新增 `PERSISTED_UNVERIFIED`（`warn`，文字「已合并 · 未做语义复验」），只给「返回写作台」；**不冒充** `PERSISTED_VERIFIED` |

为什么保留 `AWAITING_SEMANTIC` 这个档位而不是删掉它：作者要的是"能自己选"，不是"永远不用验"。
所以默认仍是复验优先（主按钮），跳过是**第二选择**且必须看见代价 —— 顺带把"合并后界面还写着未复验"
这个真实缺陷一起修了（旧实现合并完仍停在 `AWAITING_SEMANTIC`，作者会以为没合并成功）。

### 8.2 新增：复验进行中的进度条

| 要素 | 实现 |
|---|---|
| 进度条 | 工作区自己画一条**不确定**进度条（`#rw-progress`，来回跑动）；一次付费调用不可分割，拿不到内部百分比，**不编数字** |
| 文案 | 阶段（启动引擎 → 逐条复验 → 仍在等待）+ 条数 + 已用时间（`0:12`）+ "界面拿不到模型内部进度" |

### 8.4 三份修稿存档 + 合并不关门（2026-10-18 作者第二轮要求）

作者原话：*"即便跳过了、合并了，我也要有个反悔的机会，让我能再次点击运行独立语义复验；
正文的话，改成能保存 3 份：审稿前、未进行独立语义复验的一份、进行过独立语义复验的一份，
无论我选择什么，都要有记录，都要有反悔的机会。"*

| 维度 | 做法 |
|---|---|
| 三个槽位 | 新增 `public/revision-archive.js`：`base`（审稿前原文）/ `unverified`（未复验候选）/ `verified`（已复验候选）。**槽位不混用**：未复验候选绝不写进"已复验"槽（那等于给没验过的稿子盖章）。判据是"**跑过语义复验没有**"而不是"全过没有"：部分合并（`PARTIAL_CANDIDATE`）也是跑过复验的候选，进 `verified` 槽；只有 `AWAITING_SEMANTIC`（跳过复验）才进 `unverified` 槽 |
| 落库位置 | 三份都以带标记标题写进服务端 `chapter_save_versions`（`修稿存档 · 审稿前原文` 等）→ 作者在现成的「🕘 历史版本」里逐条查看 / 恢复；恢复前服务端会自动把当前正文再存一份（永远可反悔） |
| 去重 | 按"槽位 + 内容指纹"去重（`hashOf`）：同一份内容不重复存；内容变了（复修一轮）才成为该槽的新记录 |
| 入口 | 工作区底栏 `修稿存档 N 份 · 查看/回退`（有存档才出现）+ 写作台收口条上同样的入口（离开工作区、刷新页面后仍在） |
| 合并后补验 | `PERSISTED_UNVERIFIED` 档位给「对已合并的候选运行语义复验（一次付费调用）」——补验一次的状态写 `reverifiedAfterMerge`，档位交回终审（`PARTIAL` / `VERIFIED` 都可能），补验通过则记入"已复验候选"槽 |
| 记录 | 本地索引 `ns_revision_archive:<chapterId>`（槽位→版本 id/指纹/时间）；索引坏了只丢去重，不影响历史版本 |
