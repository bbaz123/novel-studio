## 〇、体验方法与边界（先说清楚）

1. **隔离性**：全部体验在 `PORT=3738` + `NOVELSTUDIO_DATA_DIR=.test-data-experience` 的隔离实例进行；用户主实例（3737）与其 SQLite 数据库、OpenViking 目录未做任何写操作。新作品自动分配 32 位 hex `ov_uri`（实测 `8e960ce2654ea0bf9f14ff71ebfdcbca` 等），不占用用户主库的数字目录。
2. **AI 调用（用户已授权，共约 10 次，费用极低）**：连接测试 1 次（max_tokens=16）；直连润色 1 次（短文本）；Harness 慢通道任务约 8 轮（澄清问答 5 轮完成、蓝图确认 1 轮、成文 1 轮、另有 1 轮成文因服务进程被外部终止而中断）。精确用量可在 DeepSeek 开放平台「用量」页核对。
3. **意外事件（如实记录，反而成为一次健壮性实测）**：体验中途（20:55:18）隔离实例与用户 3737 主实例的进程在同一秒被外部终止并重启（重启后的进程携带我原命令的完整环境变量，父进程为 powershell，判断为外部人工操作）。事后核验：SQLite 数据（作品/章节/配置）零丢失（WAL 持久性有效）；代价是 Harness 任务状态仅存内存（`harnessJobs` Map），进行中的 AI 任务不可恢复——UI 轮询 404 后任务丢失。此场景已作为缺陷 [P-17] 记录。
4. **测试工具限制**：自动化浏览器窗口被遮挡时 Chromium 节流定时器，导致自动化 settle 极慢（60–90s/步），全部 UI 观察均已考虑该因素；同时这一现象直接复现了 [P-08]（ui_block 误报）缺陷。

## 一、程序员视角：架构与工程质量

### 1.1 总体评价：8.0 / 10

零依赖约束下（Node 内置 http + node:sqlite，无任何 npm 包）实现的单机小说工坊，工程素养显著高于平均水平：分层清晰（`server.js` 路由内核 + `db.js` schema + `logger.js` 观测 + `harness.js` 桥接 + `openviking*.js` 记忆库 + `public/app.js` SPA），防御意识全面（CORS 收紧、body 按字节限流、白名单表名/字段、病态输入拦截、进程树强杀、乐观锁尝试、提案制人审）。主要失分在「边界假设」：服务监听全接口却信任可伪造的 Host 头（P0），章节乐观锁锁值从不推进（P1，已实测证实），以及若干一致性与可观测性细节。作为 localhost 单机工具日常可用，但 P0 必须尽快修复。

### 1.2 亮点清单（带代码证据）

- **[G-01] 泛化 CRUD + 双重白名单防注入**：12 种资源集中在 `RESOURCE_CONFIG`（server.js:198-211），表名/字段仅由白名单键拼接、值全部 prepare 绑定（server.js:220-228、319-320），扩展新资源只需加配置行。约 120 行覆盖全部基础 CRUD，是零依赖约束下聪明的取舍。
- **[G-02] 跨作品引用一致性校验**：`validateOwnership`（server.js:250-271）校验卷/剧情线/父章节/分类/角色的 work_id 归属，防止「把 A 作品的数据写进 B 作品」；实测孤儿分类被拒（API 测试 E7）。
- **[G-03] 请求体按字节累计 + 32MB 上限**（server.js:74-120）：既防内存放大，又避免跨 TCP 分块切碎多字节 UTF-8 的经典乱码缺陷；content-length 预检。

- **[G-05] Harness 桥接工程化**（harness.js）：无 shell spawn 传参（326-339，根治 N-01 中文 ANSI 损坏，实测中文完好）；模型切换进程内互斥 + CAS 还原 + 崩溃残留侧车恢复（259-264、431-447）；taskkill /T 杀进程树；任务并发上限 2（server.js:2622-2624）；超时钳制 1s~60min（2626）；job 状态轮询接口带 tail/scan/proposals（2637-2652）。
- **[G-06] 统一日志系统**（logger.js）：SQLite + 滚动 JSONL 双写、分层（server/db/harness/ai/openviking/sync/plugin/frontend/process）、同层同消息去重、远端上报 layer 白名单（实测非法层 400，API 测试 H3）、事件循环滞后监测、进程崩溃兜底、双轨保留策略（DB 5000 条/30 天，文件 14 天）。
- **[G-07] OpenViking 集成稳健**：作品级 `ov_uri` 由 DB 触发器分配 32 位随机 hex（db.js:329-337）而非自增 id，根治多实例串作品（N-03）；离线 pending 队列 + 原子写 tmp+rename + 坏行隔离；插件经 `NOVELSTUDIO_BASE_URL` 回连发起实例（novel-tools.mjs:46-49）。
- **[G-08] 前端 XSS 白名单消毒闭环**（app.js:211-251）：DOMParser 重建白名单标签，`<a>` 仅保留 data-term-id 重建为安全词条链接；在渲染（1224）、保存（1542）、历史版本保存（1593）、历史查看（1641）四处处用，构成「渲染-保存-历史」三层一致的消毒闭环。自动保存「闭包快照 + flushSave」设计（1368-1399）与序号守卫/互斥锁/过期结果丢弃的竞态防护体系（457-458、6462-6471、2528-2535）质量很高。

### 1.3 问题清单（按严重度，每条附代码位置与实测证据）

- **[P-01] 严重 · 安全 —— 服务监听全接口 + Host 头可伪造 → 局域网暴露 API Key 与作品数据**
  - 位置：server.js:2995（`server.listen(PORT)` 未绑定 127.0.0.1）；配合 server.js:50-70（非 mutating 方法零校验；写请求无 Origin 时仅校验可伪造的 Host 头）。
  - 实测：`Get-NetTCPConnection` 显示 3738 监听地址为 `::`（全接口双栈）。同局域网攻击者可直接 GET 全部作品与掩码 Key，并用 `Host: localhost` 伪造头通过写校验，经 `/api/ai/*` 消耗真实 API Key。
  - 修复：`server.listen(PORT, '127.0.0.1', …)`；如需局域网访问再加共享令牌。
- **[P-02] 高 · 正确性Bug —— 章节乐观锁锁值从不推进，双窗口并发编辑会静默覆盖**
  - 位置：server.js:2869-2873（校验 `_if_updated_at`）vs updateRow（server.js:319，UPDATE 语句不含 `updated_at`）；前端 app.js:1545 携带 `chapter.updated_at`。
  - 实测（API 测试 D3b，套件中唯一失败项）：首次 PUT 成功后用同一旧时间戳重放，返回 200 而非 409——锁值冻结，409 只在时间戳与初始值不符时触发一次。
  - 修复：updateRow 的 UPDATE 追加 `updated_at = ?`；chapter_save 通道（server.js:2587）同样补锁。
- **[P-03] 高 · 原子性 —— settleProposals 入账与提案状态更新非同一事务**
  - 位置：server.js:1216-1243。apply 中途崩溃会留下「事件已入账但提案仍 pending」，重启后再 apply 对无 dedup_key 的事件重复入账。
- **[P-04] 高 · 数据安全 —— 前端关页/刷新无兜底落盘，800ms 自动保存窗口内可能丢字**
  - 位置：public/app.js 全文件无 beforeunload/visibilitychange 处理；autosave 与 flushSave 并发 PUT 同 `_if_updated_at` 时二次请求 409 → 重载丢字（app.js:1545、1391-1399）。
  - 修复：visibilitychange 时 flushSave（fetch keepalive）；在途保存标志/串行队列。
- **[P-05] 中 · 错误处理 —— 泛 CRUD 把一切异常映射为 400**
  - 位置：server.js:2907-2908（`catch → 400`）。DB 锁/磁盘错被伪装成客户端输入错误，掩盖系统故障。建议区分校验错误与系统错误（500）。
- **[P-06] 中 · 一致性 —— 413 实际不可达，超限请求收到连接重置**
  - 位置：server.js:79、96（`req.destroy()` 先毁 socket 再 reject）。
  - 实测（API 测试 B4）：33MB POST → 客户端 `ECONNRESET`，无 413 响应。安全目的达到，但文档化的 413 契约落空。
- **[P-07] 中 · 一致性 —— 必填字段校验错误直露 SQLite 约束信息**
  - 实测（API 测试 E8）：缺 title 返回 `{"error":"NOT NULL constraint failed: terms.title"}`。应返回字段级友好文案（如「词条名称不能为空」）。
- **[P-08] 中 · 一致性 —— 「页面主线程阻塞」监控误报未根治：窗口遮挡场景仍刷屏**
  - 位置：public/app.js startClientLagMonitor（visibilityState 判断未覆盖「可见但被遮挡」的窗口）。
  - 实测：隔离实例日志出现约 20 条 `error ui_block`（`页面主线程阻塞 58990ms` 等 59s 周期 + 6.8s~39s 散点）。v0.9.2 修复了后台标签页（hidden）场景，但遮挡窗口 visibilityState 仍为 visible、rAF 被 Chromium 节流，误报继续产生。建议叠加遮挡检测或降级为 debug。
- **[P-09] 中 · 数据隔离 —— 旧作品沿用数字目录，跨实例语义召回互相可见**
  - 位置：openviking-sync.js:77-79（旧作品 ov_uri 回填自增 id；代码注释已承认取舍）。
  - 实测：隔离实例搜索「潮汐」召回 `viking://user/default/resources/novel-studio/9/world/17.md`（用户主库 2026-09-03 导入的旧作品数字目录），score 62/43 正常但跨实例可见。新作品已用 UUID 目录（无此问题）；旧作品建议一次性迁移目录名。
- **[P-10] 中 · 可维护性 —— 前端单文件 6695 行 + 8 个 document 级监听 + 无作用域封装**
  - 位置：app.js:5300、6487、6521、6561、6601、6626、6636、6644；`$`/`$$`/`state` 及全部函数挂 window（app.js:2-5）。建议包一层作用域、拆分 action 注册表。
- **[P-11] 中 · 性能 —— 编辑器每次 input 全文统计字数**
  - 位置：app.js:1251-1256 → 397-399（`wordCount(editor.innerText)` 强制回流 + 全文 DOM 解析，未复用 chapterWordCountCache）。大章节逐键卡顿，建议节流 + 增量统计。
- **[P-12] 中 · 安全细节 —— Key 掩码首 6 尾 4、≤8 字符全量回显；Key 驻留前端内存**
  - 位置：server.js:276-280；前端以 `config.api_key` 存在性判断直连（app.js:2604）。建议后端只返回 `has_key: boolean`，掩码改为首 3 尾 2 或纯布尔。
- **[P-13] 中 · 健壮性 —— 远端日志上报无速率限制且逐次同步落盘**
  - 位置：server.js:2700-2728（每次 POST 触发 flushLogs：appendFileSync + DB 事务）。本机进程可高频刷写阻塞事件循环。
- **[P-14] 中 · 性能 —— /api/search 被语义检索拖慢**
  - 位置：server.js:2145（await semanticSearchMerge）。OV 慢时搜索阻塞 10s+，建议召回并入短超时路径或异步降级。
- **[P-15] 中 · 数据 —— 无 schema 版本化迁移**
  - 位置：db.js:297-325（试错式 ALTER + 逐启动全表时间戳归一化 O(n)）。建议引入 schema_version 表。
- **[P-16] 中 · 体验 —— 无路由历史（pushState）、模态框无 focus trap/aria-modal、移动端仅 900px 单断点**
  - 位置：app.js:66-86、319-333；styles.css:865。桌面单机定位可接受，移动端不达标。
- **[P-17] 中 · 健壮性 —— Harness 任务仅存内存，服务重启即丢失（本次实测复现）**
  - 位置：server.js harnessJobs Map（无持久化）。实测：服务被外部终止重启后，进行中任务轮询 404、生成物不可恢复；建议任务状态落库 + 重启后标记 interrupted，UI 提示可一键重试。
- **[P-18] 低 · 一致性 —— 人物关系删除不刷新角色卡同步**：openviking-sync.js:267-277（删除后 lookupRow 为 null 直接跳过）；**[P-19] 低 · 一致性 —— categories 变更不触发记忆库同步**：server.js:2858/2884/2900 通知了但 syncChange 无对应 case（openviking-sync.js:299-300）。

### 1.4 架构总结

单文件路由内核 + 职责明确的伴生模块：`db.js` 管 schema/索引/迁移，`logger.js` 管双写观测，`harness.js` 管 dsh 子进程桥接，`openviking.js` 管传输与离线队列，`openviking-sync.js` 管渲染与增量同步，`novel-tools.mjs` 管模型工具面。泛化 CRUD（约 120 行覆盖 12 种资源）是零依赖约束下很聪明的取舍；代价是资源特化逻辑（乐观锁、掩码、级联同步）散落在外围 if 判断里，已出现「锁写了但没生效」的断裂。安全模型以「本机即信任边界」为前提，CORS/Origin/掩码为纵深，但监听绑定缺失使边界可被 LAN 突破。

## 二、专业小说作者视角：创作工作流与工具链

### 2.1 总体评价：8.5 / 10

这是目前我见过的把「结构化创作方法」落到工具里最完整的本地写作软件：从作品设定（世界观词条/角色卡/剧情线/大纲/长期记忆）到正文写作（蓝图→成文→审稿→写回→伏笔回收），再到 AI 协作（一次一问澄清协议 + 反 AI 腔红线 + 上下文透明预览），构成了一个能真正支撑长篇连载的闭环。最大的价值不是「AI 帮你写」，而是「AI 先理解你的故事再动手」——澄清协议与蓝图机制实测质量达到专业编辑陪谈水准。主要短板在节奏控制（澄清轮数偏多、缺「一键写到底」）与任务中断无续传。

### 2.2 完整写作工作流实测记录

1. **建书 → 定调**：新建作品字段含每章目标字数/总章数/故事结构/叙事视角/正向风格要求，作者注支持。示例《雾都缝匠》一键导入 5 秒即得 2 卷 3 线 6 章 + 4 角色卡 + 5 世界观词条 + 伏笔与状态事件的完整示范。
2. **设定体系（五页签）**：剧情线（主线+支线+章节时间线）、大纲（思维导图/列表双模式）、设定库（分类+标签+词条详情，可关联正文）、角色卡（姓名/身份/外貌/性格/背景/当前状态/别名称呼/对话示例/系统提示）、长期记忆（故事摘要+版本管理+待确认提案+章节级作者注）。字段专业度向 SillyTavern 级工具看齐，且互相关联（剧情线级角色状态、伏笔跨章节跳转）。
3. **正文写作**：富文本（加粗/斜体/下划线/H2/引用/列表/编号）、自动保存 + 实时字数（纯文本口径，实测 401 字准确）、单/双/三栏布局、历史版本（手动快照/查看/恢复）、选中文字关联设定词条（悬停预览/点击跳转）、右侧参考面板六页签（设定/角色/伏笔/红线/上下文/AI）。
4. **AI 协作（旗舰功能，全部真实付费实测）**：
   - 需求确认框明示扣费（「此过程会消耗 AI 调用额度」）+「直接开始」跳问选项；
   - **澄清协议一次一问**，实测提问质量实录（三轮）：
     - Q1：「沈砚看清那三个字时的反应，基础设定是哪种：A. 他认得林修远——这孩子失踪前就来过拾线坊；B. 素未谋面，但这个名字勾起了他与三年前有关的某段旧事？」
     - Q2（承接我的回答继续深挖）：「三年前警方请你辨认物主的那件旧物，是 A：林修远失踪案调查中送到你手上的随身旧物……还是 B：与失踪案无关的例行委托……纯属巧合，又不像巧合？」
     - Q3（戏剧结构层）：「这层悬念你希望揭给谁看——A：悬念对读者揭开，对她仍是雾；B：她的记者直觉当场咬住他那一顿……交出半句真话……两人同时被钉在那桩旧案边上？」
     - 「直接开始」模式下仍先问一个收尾结构问题，且精确知道本章字数、第二章大纲排布：「第一章现有正文约五百多字……而大纲里『谈条件、约定隔日上门』和顾绣禾夜留红绳结都排在第二章。那这一章剩余约 1400 字，你希望主线写到哪收尾：A……B……C……D……」
   - **章节蓝图六要素**（确认弹窗可逐项修改）：场景目标/情节点（3-8 条）/冲突与转折/出场角色状态变化/下一章钩子/参考设定（回扣的设定与伏笔），蓝图吸收了三轮澄清的全部决定（选 B、针法秘密留白、半句真话），并落库参与后续上下文与一致性核对；
   - **成文**：进度卡阶段文案真实（「正在按反馈重新规划蓝图…」「正在按蓝图成文（这一步最慢，通常 2–6 分钟）…」），可随时停止；
   - **直连润色**（秒级通道）实测：原文「他缓缓地睁开了眼睛，那双眸子仿佛蕴含着星辰一般的光芒，声音低沉而富有磁性，仿佛能拨动人的心弦。」 → 润色后「他徐徐睁开双眼，眸中似有星辰流转，嗓音低沉而富有磁性，仿佛能轻轻拨动人的心弦。」（去除「缓缓地/蕴含着…一般/的声音」AI 腔冗余，保留原意，5.9s 返回）；
   - **成稿闭环**（代码级核验）：审稿→逐条勾选确认→修稿→段落级差异预览→合并写回（旧稿自动存历史版本）+ 红线扫描返回 + 一致性核对（未闭合伏笔/出场角色状态/事件账本 vs 正文）+ 伏笔回收自动标记。
5. **上下文透明**：「上下文」页签可预览 AI 实际收到的分层装配、出场角色（可勾选强制带入）、语义召回命中与相关度（实测相关度 62/43 显示正常，不再是 8800%）。作者第一次能看见 AI「脑子里装了什么」——这是对写作工具信任度的关键设计。
6. **红线体系**：默认反 AI 腔红线 + 豁免词整词放行 + 正向风格契约，随上下文注入。润色与蓝图实测均未见 AI 腔词。
7. **导入导出**：TXT/Markdown 按标题自动拆章（实测 3 章→3 章）、EPUB 零依赖解析、整书 TXT/MD/单章 TXT 导出（中文文件名 RFC5987 正确）。

### 2.3 作者视角亮点

- **[W-01] 澄清协议是灵魂**：一次一问、问题有明确选项且层层递进（人设→旧案→悬念结构→收尾档位），答完立即被蓝图吸收。这是我见过最接近「和懂行的编辑聊故事」的 AI 交互。
- **[W-02] 蓝图先行**：先规划后成文，六要素完整，且蓝图落库成为一致性核对锚点——防止 AI 写着写着跑偏，是长篇连载的核心痛点解药。
- **[W-03] 先确认再扣费**：AI 写作/批量生成均明示消耗额度，杜绝误触。
- **[W-04] 伏笔账本闭环**：未闭合/已回收/已废弃分组、埋设章节跳转、正文回收自动标记 resolved、成文后一致性核对。专业作者手写的「伏笔清单」被工具化了。
- **[W-05] 记忆与提案**：AI 生成的事件/记忆先落提案由作者勾选，防止 AI 篡改故事账本——对「我的故事我做主」的作者至关重要。
- **[W-06] 历史版本**：手动快照/自动备份/恢复，写作安全感十足。
- **[W-07] 防 AI 腔是产品级卖点**：红线+豁免+正向风格契约，且全程可感知可管理。

### 2.4 作者视角短板

- **[W-08] 澄清轮数无上限感**：一次一问很专业，但连续 3-5 轮后「先写出来再改」的冲动会被抑制；建议每轮问题旁提供「够了，按现在理解直接写」的一键（当前「跳过提问直接生成」藏在按钮组里且语义是跳过全部提问，缺「本轮答完即止」）。
- **[W-09] 请求级字数未被蓝图响应**：我在需求里写「约 400 字」，蓝图目标字数仍为作品配置的 2000（占位提示称「未指定长度时按作品配置」）。需求里的长度约束应覆盖作品默认值或至少在蓝图弹窗里让作者看到并修改。
- **[W-10] 成文 2–6 分钟偏长**：进度卡文案诚实（「这一步最慢」），但对连载日更作者，单章成本是「时间×轮数」；建议蓝图确认后提供「后台排队生成，完成后通知」。
- **[W-11] 任务中断无续传**：服务重启（哪怕是被动重启）即丢进行中任务（本次实测）。长篇生成中途中断的挫败感极强，建议任务落库 + 断点续传或一键重试。
- **[W-12] 参考面板发现成本**：两栏模式下右侧面板收起，新作者要切到三栏才发现六页签参考面板；建议两栏也保留窄面板入口或首次引导提示。
