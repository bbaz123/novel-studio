# 恢复条上三类提示缺少关闭出口（2026-10-04）

## 报障（三轮，同一个形状）

第一轮，编辑器上方：

> 🗂 有未应用的生成稿（219 字，22:48:44）　[取回生成稿]　[预览]

作者原话：**"缺少个关闭按钮，如果我永远也不想要这个版本了，缺少关闭按钮"**。

第二轮（补完第一处后，作者截了同一条恢复条的另一段）：

> ⏳ AI 写作：已完成，结果待应用 · 产出 1711 字符　[取回结果并应用]
> ⏳ AI 写作：已完成，结果待应用 · 产出 75 字符　[取回结果并应用]
> ⏳ AI 写作：已完成，结果待应用 · 产出 135 字符　[取回结果并应用]

作者原话：**"这些呢"**。

第三轮（补完前两处后，我报告里问"审稿那行要不要一起补"，作者回一个字）：

> 🔍 上次审稿（N 个问题，时间）　[查看]

作者原话：**"要"**。

## 为什么会这样（根因）

这条恢复条上的每一行都**只有"要它"的出口**，没有"不要它"的出口：

| 行 | 给的按钮 | 缺的 |
| --- | --- | --- |
| 🗂 有未应用的生成稿 | 取回生成稿 / 预览 | 不要这一版 |
| ⏳ AI 写作：结果待应用 | 取回结果并应用 | 不要这条结果 |
| 🔍 上次审稿 | 查看 | 不看这条提示 |

而三行的显示条件都是"库里还有一条没处理掉的记录"：

- 草稿行：`chapter_save_versions(kind='draft' AND draft_applied=0)` 里还有一行（`getLatestDraft`）；
- 任务行：`harness_jobs` 里 `kind NOT LIKE '%:applied'` 且（跑着 / done 且有产出 / 失败）；
- 审稿行：`chapter_reviews` 里该章有记录（`getLatestReview`，每章保留最近 10 份）。

只要那条记录在，提示就一直在——不点"取回/查看"就永远挂在编辑器上方。
于是"我不想要这一版/这条结果/这条提示"在界面上**无法表达**：作者只能靠"取回再撤回"或干脆忍着。

这不是样式问题，是**状态机少了一个终止动作**：

- 草稿只有"未应用 → 已应用"，缺"未应用 → 已关闭"；
- 任务只有"待应用 → 已应用"，缺"待应用 → 已放弃"；
- 审稿只有"已生成 → 已查看"，缺"已生成 → 不再提示"。

（同类出口此前已经补过一次：编辑器被误清空时的「取回历史版本 / 确认清空本章」。
那次事故的教训是"作者看到状态却没有任何可点的动作"，这次是同一个形状出现在三行上。）

## 修法（第一处：生成稿那一行）

新增第三个动作：**关闭**（标记 `draft_dismissed=1`），语义严格限定在"提示"上。

- `db.js`：迁移新增列 `chapter_save_versions.draft_dismissed INTEGER NOT NULL DEFAULT 0`
  （默认 0 → 存量草稿语义不变，仍然照常提示）。
- `server.js`：`getLatestDraft` 多一个 `AND draft_dismissed = 0`；新增 `dismissDraft()` 与
  `POST /api/novel/draft/dismiss`（缺 chapter_id → 400，章节不存在 → 404，幂等）。
- `public/app.js`：草稿那一行加 `✕ 关闭`（带 confirm）；处理函数 `dismissChapterDraft()`；
  新增 `refreshRecoveryBar()` 就地重画恢复条。

三个刻意的取舍：

1. **只标记，不删除内容。** 与 `draft_applied` 同一思路：关闭是关于**提示**的动作，
   不是关于内容的动作。误点一次不该让几万字的产出凭空消失。关闭后该行仍在版本表里，
   长度逐字节不变（冒烟 D4 验证）。
2. **不动正文。** 关闭不经过任何写正文的通道（`PUT /chapters/:id` / `chapter_save` /
   `adopt` 都不参与），冒烟 D5 验证章节内容逐字节一致；前端回归 P-DISMISS-4 验证
   这一动作只发一个请求（`/novel/draft/dismiss`）。
3. **只关这一份，不连坐更早的。** 这一点与采纳（`mode='up-to'`）**故意不同**：
   采纳意味着"最新那一版已经进正文了"，更早的自然作废；而关闭意味着"这一版我不要"，
   此时更早的那一版**恰恰可能是作者想回退的**——静默把它一起关掉就是误伤。
   所以关掉之后如果还剩更早的未应用草稿，界面按服务端返回的真值把它显示出来
   （P-DISMISS-5），而不是假装这一章没有草稿了。

## 修法（第二处：长任务那些「结果待应用」行）

同一形状：那一行只有「取回结果并应用」——也是"要它"。而只要
`GET /harness/recoverable` 还返回这条任务（`kind NOT LIKE '%:applied'`），
行就一直在，哪怕它是一周前那次没用的产出（截图里那三条正是 10-01 挂在第 119 章的）。

- `public/app.js`：任务行加 `✕ 关闭`，处理函数 `dismissJobResult(jobId)`。
- **没有服务端改动**：复用既有 `POST /harness/mark_applied`
  （把该行 `kind` 追加 `:applied`，恢复条查询据此排除）。

四个取舍：

1. **只给"已经结束"的行加关闭**（判据是 `!st.canResume`）。正在跑/排队的行只能
   停止或接回——把一条**还在跑**的任务"关掉"，等于把"它还在跑"这件事藏起来，
   那是误导，不是关闭。
2. **先等服务端确认，再收起本地那一行。** 既有 `markJobApplied()`（自动路径：打开结果弹窗/
   展示审稿报告时顺手标记）是发完就不管的；作者亲手点的关闭若只改本地，刷新后提示会
   自己回来——那比不关更糟。所以 `dismissJobResult` 用 `await`，失败就保留该行并报错（P-DISMISS-9）。
3. **复用 `:applied` 这个开关，语义放宽为"这条产出不用再提示了"**（原义偏"已应用"）。
   两者对界面的意义相同，全仓也**只有**恢复条这一个 `LIKE '%:applied'` 的消费点，
   没有计数/报表把它当"采纳次数"，所以不新增列、不重启服务。
4. **不删内容**：`harness_jobs.output` 原样保留（关闭后仍可按 id 从
   `GET /harness/recovered` 取到），正文一个字不动；界面上则不再有那条入口。

## 修法（第三处：🔍 上次审稿 那一行）

同一形状的最后一处：那行只有「查看」，而 `chapter_reviews` 每章保留最近 10 份，
于是"看过一次"并不等于提示会消失，它总能再顶上来。

- `db.js`：迁移新增列 `chapter_reviews.dismissed INTEGER NOT NULL DEFAULT 0`。
- `server.js`：`getLatestReview` 带上 `dismissed`（**不过滤**）；抽出 `reviewForClient()`
  （GET 与关闭动作共用一份形状，避免两处漂移）；新增 `dismissReview()` 与
  `POST /api/novel/review/dismiss`。
- `public/app.js`：那行加 `✕ 关闭`；判据在客户端（`reviewOk = … && !r.dismissed`）；
  处理函数 `dismissChapterReview()`（同样等服务端确认再收起本行）。

与草稿/任务两处**故意不同**的一点：**服务端不过滤已关闭的审稿**。

- 草稿/任务关掉后，那条记录在恢复条语义里就"用掉了"，所以过滤在服务端；
- 审稿不同：作者说"别再提示我"，不等于"把报告藏起来"——他可能从别处回看报告。
  所以关闭只写一个标记，`GET /novel/review` 照常返回该行（带 `dismissed: 1`），
  由恢复条自己决定不显示。冒烟 R3 专门固定这条差别。

## 一个需要作者确认的观察

重启服务后核对真实库时发现：第四章那份 219 字的草稿（`chapter_save_versions#57`，
`ch=122`）**已经被标记为已关闭**（`draft_dismissed=1`），所以它的那行提示已经消失。

- 内容**没有被删除**：`LENGTH(content)=229`，与原样一致。
- 全仓只有 `dismissDraft()` 一处写这一列，而它只能由 `POST /api/novel/draft/dismiss` 触发；
  本轮我本人对真实库发起的唯一一次请求带的是不存在的 `draft_id=99999999`（返回 `dismissed=0`，
  不可能改到 #57）。因此这次关闭只可能来自浏览器上的那次点击。
- 后续证据：库里被关闭的草稿集合是 **`[32, 35, 57]`** —— #32/#35 都在第 119 章（作者当时正开着
  那一章、也正是他截图里那三条任务所在的位置），说明作者确实在连续使用这个新按钮。
- 如果这不是作者本人点的：一条 SQL 即可放回（内容还在，没有不可逆损失）：
  `UPDATE chapter_save_versions SET draft_dismissed = 0 WHERE id = 57;` 再刷新页面。

## 自查：本轮我自己的两个错误（都在交付前被抓到）

1. **验证跑在了过期副本上。** 迁移测试原本用 `fs.copyFileSync` 只复制 `novel.db`，
   而库跑在 WAL 模式 —— 副本漏掉了仍在 WAL 里的上一轮 `ALTER TABLE`，
   于是"迁移前"读数是个假前提（同一错误在本项目已是第三次出现）。
   修正：改用 `VACUUM INTO` 产出自包含副本，读数立刻与真实库一致。
2. **前后两次统计口径不一致，制造了一个假故障。** 迁移前用
   `kind='draft' AND draft_applied=0`（那时新列还不存在），迁移后却多加了
   `AND draft_dismissed = 0`，读数 8 → 5，脚本据此报"迁移改动了 3 行"并给出
   `MIGRATION_FAILED`；真实情况是那 3 行早被作者自己关掉、迁移一行未改。
   修正：前后口径逐字对齐（8 → 8），新列上的标记改用**集合相等**判断
   （新增误标 0、丢失标记 0）。

两条都已写入 OpenViking 长期经验（更新既有条目，未新建重复文件）：
`SQLite库裸文件复制产生损坏副本.md`（追加第二次复发 + 「首选 VACUUM INTO」规则）、
`汇总统计口径未对齐导致覆盖率为零.md`（追加同族复发 + 「前后口径必须逐字对齐」规则），
写入后均已回读同一 URI 确认内容。
