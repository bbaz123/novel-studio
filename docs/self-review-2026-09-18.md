## 一、本轮修掉的问题（10 项，按严重度）

### 1）【高·用户可见】S2 内联的红线扫描读错字段名 → 审稿提示词里是 `undefined×N`
- 位置：`public/app.js` 的 `runArticleReview`（组装 `redlineScanText` 处）
- 现象：前端读 `h.word`，而 `POST /api/novel/scan` 的命中项字段是 `pattern`
  （`server.js` 的 `scanAgainstRedlines` → `hits.push({ kind, pattern, note, count, sample })`）。
  同文件既有 UI（`redlineScanSummaryHtml`）用的就是 `h.pattern`。
- 后果：S2 这个改进**完全失效且更糟**——模型收到的是「命中 6 处：undefined×3、undefined×2」，
  拿不到任何真实红线词，却同时被提示词要求"必须与扫描结果一致"（诱导编造）。
- ⚠️ **取证边界（第五轮独立复核提出，成立）**：S2 这个功能本身是本会话**同批新增**的，
  有缺陷的版本只存在于**未提交的工作区**，因此 `git log`/`git show` 里看不到"删掉 `h.word`"那一行 ——
  修复提交是一次性把（带缺陷的）功能整体加进去的。**不要**据此认为"这个缺陷没发生过"：
  可复核的证据是修复后的断言（98c/98d/98e 三条，其中 98e 是跨文件字段契约）。
- 修复：抽出 `buildRedlineScanText(scan)`（字段以服务端契约为准，带兜底），
  前端测试补三条断言（渲染不含 `undefined`、零命中不编造、**跨文件字段契约**），
  并把测试桩从 `{word:…}` 改成服务端真实形状。
- 根因：**字段名契约只在一侧核对**。这类"名字对不上"在本项目已发生三次
  （`plainText`、追踪的 `nodes`、这次的 `word`）——每次都是"写的时候凭印象，没有一处能从契约反查"。

### 2）【高·静默降级】质量档的 `reasoning_effort` 在 `/harness/job` 入口被丢掉
- 位置：`server.js` 的命名任务入口（`POST /harness/job`）与 `generateNovelFromHarness`
- 现象：前端「AI 自动创建小说」按质量档发 `model + reasoning_effort:'high'`，
  而该入口**根本没读 `body.reasoning_effort`**，`createHarnessJob` 与 `generateNovelFromHarness`
  也都没有这个参数 → 字段一路被静默丢弃。
- 后果：模型档位合并成一个名字之后，强度是质量档**唯一**的补偿信号（`ai/policy.mjs` 文件头写得很清楚：
  "去掉它，质量档就退化成和快档一模一样"）。这条路径上的"质量优先"正好失效，而且不报错、界面看不出来。
- 修复：入口读取 + 与 `/harness/run` 同一套非法值 400 校验 + 透传给作业与运行体；
  旧的同步路由 `POST /harness/generate_novel` 也补上（同一功能两个入口不该有不同质量档）。
  护栏：`verify-named-jobs.mjs` 新增两条断言（并把断言**限定在 job 段落内**，见下一条）。
- 根因：**"前端发了"被当成"后端收了"**。字段跨层传递没有一处做对账。

### 3）【高·护栏本身红了没人知道】`verify-named-jobs.mjs` 在本会话改动后已经变红
- 现象：该文件的断言用**精确字符串**匹配 `model: QUALITY_AI_MODEL, signal }`，
  而本会话给 `compressStoryMemory` 插入了一行 `reasoningEffort: …`，把这段字符串**按行拆开**了。
- 取证：`git show HEAD:server.js` 上两条旧断言为真；当前工作区为假 → 说明**红是从本会话开始的**。
- 后果（比"红"更值得记）：这一条校验器保护的正是"命名任务接线"，而 #2 的缺陷就在同一段代码里。
  **红灯与真 bug 相邻，却没人看** —— 因为交付时只跑了"手挑的 4 个校验器"，没有跑聚合入口。
- 修复：断言改成 `[^}]*` + `signal\s*\}` 的**语义正则**（参数变多、换行都不再假红），
  并新增 3 条针对 #2 的断言；随后用**变异测试**逐条确认（8 个变异体，每个都被对应断言抓住）。
- 新增规则见第五节 R3。

### 4）【中·自我矛盾】修稿差异预览的计数口径 + Markdown 字面量泄漏
- 位置：`public/app.js` 的 `showReviewDiff` / 两个调用点
- 现象：第三个参数被当成"清单条数"写进标题（「按 N 条清单修改」），
  但"接回进度"那条路径只知道**实际改好**几处，于是传进去的是 `applied.length`
  → 弹窗标题说「按 0 条清单修改」而正文说「有 2 条改动没能自动定位」；同一份产出两个互斥的数。
  另外正文里的 `**没能自动定位**` 是 Markdown 写法，在纯文本弹窗里会原样显示星号。
- 修复：第三个参数改为**带标签的对象** `{ checklist, applied, notes }`，标题按已知量分别措辞；
  删掉 `**`；新增 4 条断言（含"未定位条数与正文一致"）。
- 根因：一个参数位承载两种量 → 迟早自相矛盾（与第二轮"同一量对外只允许一种口径"同源，方向相反）。

### 5）【中·语义失效】`detectPluginInstall` 的 `is_link` 恒为 true
- 位置：`server.js` 的 `detectPluginInstall`
- 现象：`isLink = st.isSymbolicLink() || Boolean(st.isDirectory())` —— 任何目录都为真。
- 后果：`GET /api/env/tools` 把这个字段当对外契约返回；今天前端恰好没用它，所以没有可见症状，
  但下一个消费者（或"复制安装 vs 链接安装"的提示）一定会被骗。
- 修复：只认 `isSymbolicLink()`（Windows 的 junction 在 lstat 下也是 symlink），
  "指向本仓库"仍由 `points_here`（realpath 比较）判断。

### 6）【中·多源】直连请求超时与策略表不同源
- 位置：`server.js` 的 `AI_REQUEST_TIMEOUT_MS`
- 现象：写死 `30 * 60 * 1000`，与 `ai/policy.mjs` 的 `LONG_AI_TIMEOUT_MS` 同值重复。
- 后果：前端的直连长生成是按 `longAiTimeout()` 在等的；策略表一旦调大（比如 45 分钟），
  直连路径仍会在 30 分钟被 `abort()` 掐断，而 AbortError 的形态**看起来像网络故障**，排查方向会被带偏。
- 修复：改为 `= LONG_AI_TIMEOUT_MS`（单点），并写明为什么两者必须同源。

### 7）【中·与插件不一致】OpenViking 凭证链与插件差两处
- 位置：`openviking.js` 的 `openVikingConfigPaths` / 凭证阶梯
- 取证：逐行读了插件 `@openviking/dsh-memory-plugin/shared/credentials.mjs`。
- 现象：① 两个 env 覆盖点不做 `~` 展开（插件有 `normalizePath`）；② 没有实现
  `OPENVIKING_CREDENTIAL_SOURCE=auto|env|cli`（插件有 `sourceMode`）。
- 后果：作者按插件习惯把 `OPENVIKING_CLI_CONFIG_FILE` 写成 `~/.openviking/ovcli.conf` 时，
  **插件读得到、工坊读不到** → 工坊连默认地址、dsh 侧连真实地址，症状是"界面显示已连接，
  AI 写作却召回不到" —— 正是该模块开头要消灭的那类问题。
  （本机当前**没有**设这两个环境变量，所以是潜在缺陷、不是正在发生的事故。）
- 修复：照抄 `normalizePath`（支持 `~`、`~/x`、相对路径）与 `sourceMode`（cli/env 两种模式）；
  文件头改为**逐档对齐**的准确描述，并列出"刻意不实现"的三项（MCP_URL、account/user/peer 组、
  旧安装的 ovcli 形状兼容分支），避免下次被当成漏做去补。
- 测试：`env-tools-test.mjs` 新增 A15–A18（`~` 展开、相对路径、cli 模式、env 模式）。

### 8）【低·正确性】新增的两个环境路由把请求体错误吞成"缺少字段"
- 位置：`server.js` 的 `POST /env/open_folder`、`PUT /env/dsh_repo`

- 修复：新增 `readBodyOrError(req, res)`，按真实原因回 400/413，并注明"报错与原因无关"是本项目栽过的坑。

### 9）【低·会误导下一个会话】`runGenAskLoop` 的历史注释仍写 `deepseek-v4-pro`

## 二、被证据推翻的结论（同样重要：避免下次重复"修"不存在的问题）

### 1）"蓝图直连的前置判据几乎恒真，直连永远用不上" —— **不成立**
- 复核给出的机制是：`manifest[].dropped` 是逐层常规裁剪量 → 真实章节必然 `> 0` → 函数恒真。
- 实测（读真实数据基线，逐用例套用 `aiContextTruncated()` 的判据）：
  - `.p1-baseline/baselines-p5-real`（真实库 20 个用例）：**直连可用 19/20**；
  - `.p1-baseline/baselines-p5`（压力数据 50 个用例）：直连可用 34/50（被挡的都是 w16 这种超长作品：一次 7–9 层被截）。
- 另外 `dropped > 0` 与 `truncated === true` 在 `ai/context/assembler.mjs`（`renderSection`）里**恒同时出现**
  （`emitted = bodyLength` 时 `truncated:false`）→ "只看 truncated、去掉 dropped"这个建议**不改变任何行为**。
- 结论：这是**设计内**的取舍（截断时用慢通道，因为只有它能用工具取回被裁掉的原文），不是缺陷。
  已把这份实测数据留在报告里，避免下次再被同一推论带偏。

### 2）"`frontend-test` 的 81/82 是假绿（抢救分支从未执行）" —— **成立**（但第一次复核的取证方式有误）
- 复核给出的理由是"该载荷是合法严格 JSON，`if (viaStrict) return viaStrict;` 直接返回"——**结论对**。
- 我第一次自己验证时得到相反结论（"严格解析失败，所以走了抢救"），原因是探针按
  `const broken = ` 找变量，抓到了**另一个同名变量**（审稿报告那段的载荷）。
  这属于"验证脚本自己出错"，见第五节 R4。
- 修复：把两层分开钉住——`80b` 用前提断言声明"本组载荷是合法 JSON，故 81/82 只覆盖全角引号"，
  新增 `80c/80d` 用**真正无法严格解析**的载荷（值里带裸引号）覆盖抢救分支（前两层都失败才会走到）。
- 顺带确认：`extractJSONFromText` 的"修引号重试"只处理 `"…" , } ]` 这类**分隔符附近的多余引号**，
  它并不是通用 JSON 修复器（实现与注释的措辞容易让人误判能力边界，这里一并记下）。

### 3）"接口回归 178/178 在算术上不可能，恒为奇数" —— **不成立**
- 复核是按 `record()` 调用点静态推算的；实测在隔离实例上是 **178/178 通过**（本轮跑了两次，第二次全绿）。
- 教训：静态推算可以提示"去核一下"，但不能替代实跑；**结论要标成"未能证实"**。

### 4）其它"确认不是问题"（避免重复排查）
- `jobMeta` 的作用域：在 `while` 循环体内声明，三处引用都在同一块内（`node --check` 之外还做了人工核对）。
- `HELP_TEXT` 19 个键 ↔ 19 个 UI 调用点：双向对齐，无死条目、无悬空引用。
- `data-action` ↔ `handleAction` 全量交叉比对：仅 `search-go` / `semantic-toggle` 由专用监听器处理（既有设计）。
- 幽灵调用护栏：经变异测试确认仍能抓到重新引入的 `plainText(...)`，且已能正确识别解构声明（不假红）。
- 四份历史报告/README/CHANGELOG/`ai/README`/`ENGINE.md` 的相对链接与锚点：全部有效。

## 三、本轮"验证脚本自身"出的错（记下来，因为它们会伪装成产品缺陷）

1. **探针抓错变量**：按 `const broken = ` 取载荷，取到同名的另一处（见上）。
   → 改为"用 JS 求值取字面量"并打印转义后的原文；两种取法一致性也要断言。
2. **变异测试的比对键写错**：断言名用的是短键（`A1`），但变红清单里是全名（`A1 读取 effort`），
   `includes()` 恒为假 → 8 个变异体全被判成"未被抓住"。实际每个都红了。
   → 变异测试也要"先证明自己会报红"（自检一条已知必红的变异体）。
3. **测试实例的环境变量不一致**：第一次跑 `api-test-suite` 时没带 `NOVELSTUDIO_DATA_DIR`，
   套件按自己的默认值去 `.test-data-trace` 找追踪文件 → 3 条"封卷"断言 ENOENT 假红。
   → 起隔离实例与跑套件必须用**同一份**数据目录（文件里已写明约定，我漏读了）。

## 五、根因与防复发规则（同步写入 OpenViking 的自动注入偏好文件）

**R1 · "前端发了"不等于"后端收了"——跨层字段要有对账点。**
本轮最严重的技术缺陷（#2）没有任何报错：字段在中间一层被丢掉。
规则：任何跨层传递的**可选**字段（强度、超时、模式、归属 id），
写完必须在接收端留一处"读它"的痕迹，并有一条断言能证明"链路通了"；
`verify-named-jobs.mjs` 里新增的三条就是这种痕迹的模板。
**并且断言要限定在该入口的代码段内**——`normalizeReasoningEffort(body.reasoning_effort)`
在 `/harness/run` 里也有一份，全局匹配会被**另一条路由**满足（本轮变异测试就是这样抓到盲区的）。

**R2 · 字段名契约只核对一侧 = 没核对。**
`h.word` vs `h.pattern` 让一个改进直接变成噪声源。规则：
读写同一个响应对象的代码分处两地时，加一条**跨文件契约断言**（前端读的字段必须出现在服务端的
`hits.push({...})` 里），并在扫描前剥掉注释（否则会把自己写的反面教材当缺陷）。这条已进 `frontend-test`。

**R3 · 手挑校验器 = 会漏掉正在变红的那一条。**
本会话交付时"4 个校验器 exit 0"，而真正保护改动面的 `verify-named-jobs` 与 `verify-phase-map`
都是红的——它们恰好是**最接近本次改动**的两个。规则：
交付前跑**聚合入口**（`verify-all.mjs`）或显式列出"本轮没跑的校验器"；
只要本会话动过某文件，就要跑**所有引用该文件的校验器**（`grep` 出 import 它的工具即可）。

**R4 · 验证脚本失败/成功，先怀疑脚本自己。**
本轮三次踩同一坑：探针抓错变量、变异测试比对键写错、测试实例数据目录不一致。
规则：写自建探针时，① 用"求值"而不是"正则抓取"取被测数据；② 加一条"已知必红/必绿"的自检样本；
③ 探针的结论要能被第二种方法复核一次（本轮画像正是靠 `git show HEAD:` 对照才定案的）。

**R5 · 同一参数位只表达一个量。**
`showReviewDiff(old, new, N)` 里的 N 在两个调用点上含义不同（清单条数 / 实际改好处数），
必然出现"标题说 0 条、正文说 2 条"。规则：一个数字只用一个含义；两种量就传**带标签的对象**，
并在弹窗里分别措辞。**纯文本弹窗里不要写 Markdown 的 `**`。**

**R6 · 清理/删除类改动的"注记"要穷举，不能举例。**
历史报告的注记只列了三类过时表述，于是 §6.2 里"分批 `batchWrite`"这条被删除的实现继续躺在文档里。
规则：删除一个能力时，`grep` 全部文档命中的**每一处**都在注记里点名（或改成"以代码为准"的通用措辞），
并显式写"注记不求穷举"是不可接受的——它会造成"除此外都准"的错觉。

**R7 · 与外部实现（插件/SDK）"对齐"要有取证，不能凭印象。**
`openviking.js` 声称与插件共用凭证链，实际差两处。规则：
凡写"与 X 共用/对齐/同源"，必须**逐行读过 X 的实现**并在注释里点出对齐的档位；
差的地方要显式列成"刻意不实现"，否则下一个人会当成漏做去补（或反过来相信它已经对齐）。

**R8 · 归属/清单类工具红了，先看"是不是我这一轮新增的文件没登记"。**
`phase-map` 的完整性判据让"本会话的 13 个改动没人认领"浮出水面。规则：
每轮改动收尾时，若新增/删除了文件，同时更新阶段映射（或同类清单），
否则下一次运行会把整批红灯记在别人头上。

**R9 · "永远跳过"的断言 = 安静的假通过。**（第七节的连带发现）
M26–M29 长期只能跳过，根因不是"环境不适用"，而是**隔离配方少了两行**（没把 OpenViking 的两个
配置文件 env 指进隔离目录）。规则：① 跳过必须与通过分开计数、单独列出；
② 一条断言若**总是**跳过，要当成缺陷去查（"为什么它永远跑不了"），而不是接受它。

**R10 · 跨时间窗的操作要绑定归属，不能在消费端现读"当前是什么"。**
修稿跑几分钟，`state.currentChapterId` 在此期间会变——差异预览、补丁底稿、合并写入三处都栽在这一点上。
规则：长耗时流程在**派发时**就把归属（章号/作品/任务 id）定下来，一路带到底；
消费端只读这个绑定值，不读"当前"。同源问题此前在 harness 任务归属上出现过，这次是**前端 UI 状态**。

**R11 · 测试对被测实例的写入必须无条件还原（`try/finally`），并明确"跳过 ≠ 通过"。**
这套件可能被人对着作者自己的 3737 实例跑。凡是持久化写入（配置、设置）都要在 `finally` 里还原，
且还原失败只记录不抛出（否则会顶掉真正的失败原因）。

### 一、先查证「日志一直报警慢」这件事本身（用数据，不靠印象）

- `data/logs/*.log` 11 份 + `app_logs` 表（只读打开；保留策略 5000 行 / 30 天，而当前只有 **193 行** → 历史没有被裁掉）：

  → **不是"日志一直报警慢"，而是真正慢的那一段根本没被报警**；因此"日志没报警慢"不能用来证明"生成不慢"。

### 二、改动（`public/app.js` 的 `batchGenerateChapters`）

上一轮的「写作路径提速」只改了**交互**路径（`performToolbarAIWrite`），批量那条路一直没跟过来：
每章要跑 **2–4 个慢通道任务**（蓝图 1 + 成文 1 + 补足 ≤2），而每个任务有 **≈17–18 秒**冷启动固定开销
（`README` 的实测：微型任务 直连 0.6s vs 慢通道 17.9s）→ **10 章就是 6–12 分钟纯开销**。

- **蓝图轮改直连优先**，两道保险与交互路径逐字同源：① 上下文被预算截断时**不**走直连
  （只有慢通道能用 `novel_lookup` 取回被裁掉的原文）；② 直连失败/空回复回退慢通道。
- **补足轮按缺口分档**：小缺口（<15%）直连，大缺口仍走精写内核——判据与交互路径一致。
- **成文轮刻意不动**：它同时承担事件/记忆入账与一致性核对（`novel_*` 工具），批量时没有人盯着；
  改直连就要另造入账链路，而那条链路会与下一章的作业抢服务端的 2 个并发槽（抢不到即 429，**提案静默丢失**）。
- 净效果：每章慢通道任务数 **4 → 1**（1 轮补足时约省 **52 秒/章**，10 章约 **8–9 分钟**）；
  收尾 toast 新增**本批用时与平均每章耗时**，让"提速有没有生效"当场可核对。

1. **成文轮改直连**：每章还能再省 ≈17 秒，但要付出上面那条入账链路的代价。在"不影响质量"的前提下不做。
2. **批量并行化**：**不是质量中性的** —— 第 N+1 章的上下文里「前文衔接」层取自章节正文尾部，

## 附二、追加改动：正文写作主链路（用户明确"重心在正文写作质量"）

### 1）成文轮补上内联写作纪律（质量修复）

**发现**：`WRITING_DISCIPLINE` 只内联进**蓝图轮**（`public/app.js` 的 `buildAIWritingBlueprintPrompt`）
与**审稿轮**（`buildAIReviewPrompt`），**成文轮 `buildAIWritingProsePrompt` 是唯一漏掉的一轮**。

**为什么不对称且有害**：慢通道成文靠插件人设（`harness-plugins/novel-writing/cordis.patch.yml` 人设第 2 条）
补齐纪律；而直连成文——**交互路径的默认通道**——既没有人设、也没有内联纪律，上下文里只有
【写作风格红线】的**词表**。"用具体动作、感官细节、对话潜台词替代模板句"这条**行为**纪律根本没进提示词。
README 原先写的"两条通道纪律对齐（约 250 字）"因此只在蓝图轮/审稿轮成立。

**修法**：把同一份常量加进成文轮（不另写一份），三处同源。
断言 `111a`；变异测试：删掉这一行 → **只有 `111a` 变红**。

### 2）成文流式直连的空回复：从"整章白等 + 报错"改为"重试一次 → 再回退"

**发现（本轮最贵的一处）**：`directAIWrite`（蓝图/质检/补足用）早就有"压低思考预算 + 放宽上限重试一次"
（依据是实测的"思考吃光 `max_tokens` → 空回复"），但**成文轮走的是 `streamAIDirectWrite`，它没有重试**。
更糟的是失败形态很隐蔽：服务端在空回复时回的是 `done` + `text: ''`，旧实现把空的 `text`
包成一个**真值对象**返回 → 调用方的 `if (!proseData)` **判不出来** → 既不重试、也不回退精写内核，
直接抛"AI 没有返回正文内容"。也就是说：**一次可恢复的空回复 = 用户白等一整章 + 报错**。

**修法**：把单次流式尝试抽成内部 `attempt()`（不发 `done` 时返回 `complete:false` 而**不抛错**，
让"空回复"与"半截流"成为两条不同的出口），然后：
空回复 → `reasoning_effort:'low'` + 更大 `max_tokens` 重试一次 → 仍为空才抛错，错误带 `emptyReply`，
由调用方**既有**的回退分支接管。**半截流保持原语义抛错**（绝不把残缺正文当成品交付）。

断言 `111b–111e`；变异测试：关掉重试 → **只有 `111b`/`111c`/`111d` 变红**，`111e`（半截流）不受影响。

### 3）验证

`frontend-test` **148/148**（新增 `111a–111e`）· `verify-all` **36 通过 / 0 未通过 / 8 跳过**（exit 0）。

### 4）新增规则

- **R20 · "同一条纪律内联进多条通道"这类改动，要逐通道对账，不能因为"我加过了"就当都加了。**
  本轮两处缺陷是同一个形状：一处规则（写作纪律）只加到了 3 条通道里的 2 条；
  一处恢复机制（空回复重试）只加到了 2 个直连出入口里的 1 个，而**漏掉的恰好是最长、最容易触发的那一个**。
  规则：凡是"给所有通道补同一件事"，就把通道列成清单逐条对账，并给每一条各写一条断言
  （本次 `111a` 断成文轮、`111b–d` 断成文流式口）。
- **R21 · 错误路径上的"真值空对象"比抛错更危险。** 空 `text` 被包成对象返回，让调用方的
  `if (!x)` 判空逻辑失效，于是**该回退的回退不了**。规则：返回"结果对象"的通道函数，
  要么在空结果时抛错、要么让调用方按字段判空，**不允许**用"真值但内容为空"的对象表示失败。
- **R22 · 常驻进程池必须"关闭后不再收留"**：`disposeAll` 与异步补位之间存在竞态，
  一个刚 spawn 完的进程可能在关闭之后才落地、再也没人 dispose 它 —— 服务退出就漏一个孤儿。
  规则：任何"异步产出资源"的池都要有 `disposed` 标志 + 就绪即就地退役，并在关闭时 await 在途产出。

|---|---|---|
| **A. 升级源码仓库**到含 `sdk-app` 的版本并重装依赖 | 常驻池按原设计即可用 | 从 `0.1.1-rc.2` 跳到最新，**写作任务的 dsh 组合整体改变**（人设/工具集/提示词），必须重抓基线对照；仓库里还有未跟踪的 `wudu_ch6.txt` 要保住 |
| **B. 把 harness 指向 npm 全局那份 dsh** | 它自带 `sdk-app` | ① 它**没有 `scripts.dsh`**（`bin: {dsh: lib/bin.js}`），现有 `resolveDshLaunch` 解析不出启动方式，要加一条包式启动路径；② 同样改变整条流水线的 dsh 构建（本项目自己记过"源码仓库 vs npm 全局组合结果不同"），基线要重做 |
| **C. 暂缓** | 池代码保持已验证、默认不启用 | 每任务 ≈17–18 秒冷启动照旧 |

### 现场状态（可安全回退）

- `~/.dsh-novel/profiles/novel-sdk/` 已按 A 的前提建好（`novel-writing` 是 **junction**，不是副本），
  但**当前无人引用、也不会被自动使用**（没有任何代码指向它）。
- ⚠️ 删除它时**不要**直接 `Remove-Item -Recurse`（本仓库记过：对 junction 递归删除会删到**目标内容**）。
  安全做法：`cmd /c rmdir "%USERPROFILE%\.dsh-novel\profiles\novel-sdk\node_modules\novel-writing"`，
  再删 `novel-sdk` 目录。
- 探测脚本是**故意会红**的：它红着的时候报的正是上面第 5 条。它不是一个坏掉的测试，
  而是"这个能力在当前 dsh 版本上不存在"的可复现证据。

### 新增规则

- **R23 · "能力存在"要在**目标构建**上验证，不能拿另一个构建的存在当证据。**
  本轮 `dsh-sdk-app` 在 npm 全局那份里确实存在（协议取证就是在那儿做的），
  而应用实际启动的是源码仓库那份 —— 两者差一个月的版本。
  规则：凡是"某能力可用"的结论，都要写明**在哪一份构建上**看到的，并在**真正会被启动的那一份**上复验。

## 附四、**结论反转**：不用常驻池，冷启动的 10 秒本来就能省掉

### 怎么反转的

被"附三"卡住之后，为了把"是协议写错了"与"是这份构建没有 bundle"分开，我做了一次
**对照实验**：把同一个 profile 挂到 npm 全局那份 dsh（0.1.5-rc.1，带 `sdk-app`）上跑。
结果全链路跑通，而且**握手只花了 1618ms** —— 与"每任务 17–18 秒冷启动"对不上。

顺着这个数字查下去，原因不是常驻，而是**启动方式**：

| 路径 | 命令 | 实测冷启动（子进程启动 → 模型端点收到第一个请求） |
|---|---|---|
| A 现状 | `node --import tsx/esm apps/cli/src/bin.ts` | **11,954 ms** |
| B 对照 | `node apps/cli/lib/bin.js`（仓库里**已构建好**的产物） | **1,854 ms** |
| C 生产路径 | 同上（由 `harness.js` 的 `resolveDshLaunch()` 自己选中） | **1,898 ms** |

也就是说：**那 17–18 秒里约 10 秒是"每个任务现场把 TypeScript 转译一遍"**，
而产物一直在仓库里躺着。

### 为什么这是"纯收益"而不是取舍

两条启动路径对同一 profile 组合出的配置 **`--dump-config` 逐字相同**：

```
A 行数=398  B 行数=398   差异行数=0
```

所以人设、工具集、提示词一个字节都没变 —— 变的是"要不要现译一遍 TS"。

### 落地与防陈旧

`harness.js` 的 `resolveDshLaunch()` 改为**优先预构建产物**（入口 `src/x.ts` → `lib/x.js`，
并去掉成对的 `--import <loader>`），三条回退/出口：

- 产物不存在 → 走源码；
- **源码比产物新（改了没重建）→ 走源码并在日志里说明原因** ——
  "悄悄跑一份旧 dsh"比"慢"更贵，这条是本改动的**核心风险闸**；
- `NOVELSTUDIO_DSH_LAUNCH=source|built` 可强制任一条。

判据抽成纯函数（`builtCounterpartOf` / `shouldUseBuiltEntry`）后离线钉真值表
（`.p1-baseline/test-dsh-launch.mjs`，11 条，含"时间戳拿不到时**不**换"这种保守分支）。

### 诚实的边界

- 防陈旧只覆盖 `apps/cli/src`（6 个文件，开销可忽略）。**其余包**的源码改了没重建，
  本改动**看不出来** —— 但这是既有行为：旧路径同样只现译 CLI 入口，其它包一直是读它们各自的
  `lib/`。所以这不是本次引入的缺口，写在这里是为了不让人误以为"全都防住了"。
- 端到端三个对照组由 `.p1-baseline/probe-cold-start.mjs` 手动跑（要起真 dsh，不进默认套件）；
  进默认套件的是那两条纯函数判据。

### 这一步之后，常驻池还值不值得做？

省下 10 秒后，每任务剩余冷启动约 **1.9 秒**，而常驻池要付出：新 profile、进程池、
会话生命周期、取消语义、以及"启动的是哪一份构建"的一致性风险。**收益从"最大杠杆"降到"边际优化"**。
建议：**先不做**，把"附三"的三条路留作用户决策（它们都要动 dsh 版本，代价远大于收益）。

### 新增规则

- **R24 · "慢"必须先拆成"进程启动 / 模块加载 / 模型往返"，再谈优化。**
  本项目把三者混记成"慢通道 ≈17–18 秒"很久了，于是所有优化都在"绕过慢通道"上打转
  （改直连、搬通道），而**真正的大头是一次可以完全避免的现场转译**。
  规则：任何"这段固定开销"的数字，都要能被拆解验证（本次靠假端点的**首个请求时间戳**把
  冷启动与模型往返分开），拆不开的数字不许拿来做架构决策。
- **R25 · 对照实验要先问"能不能换一个变量"，而不是"要不要换一套架构"。**
  本轮为了验证常驻池，顺手做的"换一份 dsh 构建"实验，反而暴露了真正的问题。
  规则：当一个大改造卡住时，优先做**单变量对照**，它常常直接给出更便宜的答案。
