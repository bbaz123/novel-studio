## 一、目标

两件事：让「长期记忆」这一层在上下文里的表现不再误导模型；以及建立**回答
"上下文质量到底有没有变好"** 的度量——契约里的结构化不变量回答不了这个问题。

## 二、P5-a：截断提示不再指向查不到的地方

### 2.1 一个被证伪的假设（先说这个）

我原本的判断是：「`section()` 只取前 2200 字，而 `mergeMemoryDraft` 把新进展追加在末尾
→ 模型看到的永远是最古老的内容」。**这个判断是错的。**

读源码后发现 `mergeMemoryDraft`（`server.js:1832`）是把**新进展放在最前面**：

```js
return `${delta}\n\n【此前进度】${base}`;   // 注释：新事件置顶、旧摘要压缩保留
```

头截断保留的正是最新进度。**没有修改它**——我把结论纠正过来，而不是去"修"一个不存在的缺陷。

### 2.2 真正的问题

提示语写死了「如需精确内容可用 **novel_lookup** 查证」，而 `novel_lookup` 检索的是
词条 / 章节 / 角色 / 剧情线 / 世界观 / 人物关系——**它查不到长期记忆，也查不到事件账本**。
模型照着提示去查，只会一无所获。这与 P3 建立的 `RETRIEVAL` 声明是矛盾的。

### 2.3 改法

提示语改由**该层在 `RETRIEVAL` 里声明的工具**生成；没有查回路径的层如实说明，
不编一个查不到的工具名：

| 层 | 截断提示现在写的是 |
|---|---|
| 长期记忆 | 可用 `novel_memory_read` 查证 |
| 事件账本 | 可用 `novel_events` 查证 |
| 未闭合伏笔 | 可用 `novel_foreshadows` 查证 |
| 写作红线 | 可用 `novel_style_contract` 查证 |
| 世界观 / 蓝图 / 关系 | 可用 `novel_lookup` 查证 |
| 语义召回 | 被截掉的部分当前没有查回路径（已知缺口） |

**这同时把「装配器」与「查回路径声明」绑在了一起**：以后新增层时若只在 `RETRIEVAL`
里声明工具，提示语会自动跟上；若是缺口，也会如实说。

## 三、P5-b：AI 效果埋点

### 3.1 记什么

新表 `ai_eval_events`（`db.js`），刻意**只记行为与规模，不记正文内容**——
避免把作品文本复制进一张分析表：

| 字段 | 含义 |
|---|---|
| `action` | `generate`（产出草稿）/ `adopt`（写回正文）/ `discard`（丢弃或重生成） |
| `channel` | `stream` / `harness` / `replace` / `append` / `insert` / `regenerate` / `closed` |
| `chars_in` | **送进模型的上下文字数**（取自装配器 `context_stats.length`） |
| `chars_out` | 产出正文字数 |
| `ms` | 耗时 |
| `edit_distance` | **已接线**：AI 草稿与作者最终正文的编辑距离（单位=改动字符数，见 §四） |
| `draft_key` | 把同一次生成的 generate 与它的 adopt/discard 串起来 |

### 3.2 端点

- `POST /api/ai/eval` — 记一条（埋点失败只写日志，绝不影响创作）
- `GET /api/ai/eval?work_id=` — 聚合

### 3.3 前端挂钩

在 `showAIWritingResult` 一处埋点即可覆盖三个信号——生成时记 `generate`，
把 `state.pendingAIFinal` 换成包装函数后，**所有** resolve 路径（替换/追加/插入 = 采纳；
重新生成 = 丢弃；关闭弹窗 = 关闭）自动被记账，无需逐个 case 改。
「先审稿再应用」不记账——它走审稿闭环，本次生成暂无结论，**不计入采纳率分子**。

### 3.4 实测

写入 3 生成 / 2 采纳 / 1 重生成后读取：

```json
{ "total": 6, "generations": 3, "adopts": 2, "discards": 1,
  "adoption_rate": 0.667, "avg_chars_in": 24738, "avg_chars_out": 3200,
  "avg_ms": 41000, "avg_edit_distance": null }
```

`adoption_rate` 在样本为 0 时返回 **null 而不是 0**——不用 0 假装有结论。

## 四、未做与**已接线**（诚实标注）

### 4.1 `edit_distance` 已接线（2026-09-15 晚补）

**测量点**：`PUT /api/chapters/:id`（作者改动章节后保存时）。

**为什么不在采纳那一刻量**：结果弹窗里的正文是**只读预览**（`ai-apply-preview`），
采纳写回正文必然等于草稿 → 那一刻量恒为 0、没有信息量。真正有信息量的是"作者接着改了多少"。

**草稿从哪来**：不从埋点表取——埋点表刻意**不记正文内容**。草稿本来就在
`chapter_save_versions(kind='draft')` 里（生成时就落了库），服务端直接读它。
所以整条链路**没有把作品文本复制进分析表**。

**配对规则**（刻意的、可解释的近似）：

- 取该章节**最近一条尚未测量**的 `adopt` 行；
- 只与**不晚于该采纳**的最近一份草稿配对（避免配到下一次生成的草稿）；
- 测一次就写回，之后再次保存不会重复测量（幂等，已实测）。

**算法**（`ai/edit-distance.mjs`，纯模块、可离线单测）：

| 情形 | 算法 | 说明 |
|---|---|---|
| `lenA × lenB ≤ 25,000,000` 格 | 精确 Levenshtein（两行 DP + Int32Array） | 5000×5000 实测在百毫秒量级，可放在保存请求里 |
| 超过阈值 | bigram Dice 折算 | O(n)；单位同样是"改动字符数"，可与精确值一起求平均 |

`distance` 的单位**始终是"改动了多少个字符"**，所以不同算法的行可以一起求平均。
另有 `editRatio()` 做跨长度归一（长度为 0 时返回 `null`——不用 0 假装有结论）。

**实测（隔离实例，10/10 通过）**：

```
【轮次一】采纳后「不改就保存」   ✓ 测量前 avg=null → 保存后被填上 → 距离为 0
【轮次二】采纳后「大改再保存」   ✓ 平均值落 (0, 草稿长度] 区间；采纳数累计到 2
【幂等】  重复保存两次           ✓ avg_edit_distance 不再变化
【反例】  无采纳行时保存正文     ✓ total=0 且 avg=null（不凭空产生测量）
```

阴性对照：临时摘掉 `PUT /chapters` 里的挂钩 → 端到端**失败 3 项**（`avg_edit_distance` 恒为 null），
还原后复验 10/10。单元测试另做变异：去掉"单字符无二元组"的特判 → 测试失败 1 项
（否则 `"甲"` vs `"乙"` 会被算成距离 0）。

### 4.2 记忆自动压缩仍未做 —— 但**压缩提示**此前根本没送到（已于 2026-09-15 晚修）

`mergeMemoryDraft` 仍是纯拼接、无上限，长期记忆会随章节线性膨胀。
真正的解法是在超过提示线时**自动触发 `compressStoryMemory`**——但那会**未经许可产生
API 费用**，按你「付费验证需先取得许可」的约束，我没有擅自打开。
现状缓解：`novel_memory_read` 可以取回全文（P3 已保证），压缩仍由作者点按钮或模型主动调用。

> **自审补记（F6）：那条"超过 1200 字就提示压缩"的链路此前是断的。**
>
> 装配器对每层是按 cap **从头部**截断的（`assembler.mjs` 的 `renderSection`：`body.slice(0, cap)`），
> 而压缩提示原先拼在正文**末尾**（`server.js`）。于是：
>
> ```
> 记忆越长 → 提示越靠后 → 越会被自己截掉 → 恰恰最该提示的时候提示消失
> 实测 work#16：记忆 9000 字 → 层正文 9063 字 → cap 2200 截断后，层内只剩截断提示
>   修复前：层内是否含压缩提示 = 否
>   修复后：层内是否含压缩提示 = 是
> ```
>
> **修法**：提示挪到正文**开头**（头部截断切不到它）。
>
> **代价（如实量化）**：提示现在占用 cap 内空间 —— 实测记忆层窗口让出 **63 字 / 2200 字 = 2.9%**，
> 总长不变；被挤掉的那部分仍可经 `novel_memory_read` 查回（层内截断提示已给出该工具名，I4 成立）。
>
> **影响面（逐字实测）**：50 个压力用例中 **35 个逐字未变**、15 个（全部 w16）恰好是
> 「窗口让出 63 字、总长不变、其余逐字相同」，**0 个异常**；
> 真实作品（记忆 779/781 字，低于提示线）**20/20 逐字节未变**。
> 回归基线 `baselines-p5` 已随之重抓（`baselines-p3` 作为历史参照不动）。
>
> **固化成检查**：`.p1-baseline/verify-memory-hint.mjs`（离线读基线 + 活实例自发现两模式），
> 阴性对照用**修复前的真实基线**：失败 3/3；对修复后基线：通过 3/3。

## 六、过程中修掉的两个**工具自身**的缺陷

工具也会漂移，而且比代码更隐蔽——它们不参与生产路径，坏了没人立刻发现：

1. **校验器用了过期的提示语样本**：`verify-invariants.mjs` 还在按旧的单参
   `truncationNotice(N)` 算上界（那时提示语还没有工具名），工具名一加，上界算小，
   **误报 45 处 I2 违反**。已改为从层规格导出的 `noticeSampleLength()` 派生。
2. **对照器的归一化静默失效**：`--ignore-notice` 先用手写正则（踩了字符差异，完全没匹配上
   却不报错），改成结构扫描后又踩了「提示语内部还嵌一对括号」——按首个 `）` 截断会留下
   多余的括号，把"仅提示语不同"误判成真实差异。最终改为**从层规格派生前缀 + 括号配对扫描**。

两条都指向同一个原则：**校验器不要重复实现被校验对象的逻辑，要从它那里派生。**
