## 一、已证实的缺陷

### D1（严重）追踪面板自己的数组被后端计数覆盖 → 每次会话崩溃 N 次

**证据链**

1. 日志里 19 条 `frontend_error`，栈完全一致：
   ```
   TypeError: op.nodes.push is not a function
       at traceHandleStreamItem (http://localhost:3737/app.js:1174:16)
       at es.onmessage (http://localhost:3737/app.js:1140:7)
   ```
2. 追踪记录里**一条都没有**：`session-end.summary.errors = 2`，而实际 error 级事件是 19 次崩溃 + 2 个 error 节点。
3. 根因：后端摘要里的 `nodes` 是**节点数量（number）**，前端却用扩展运算符把它合并进操作对象，把原来的 `nodes: []` 数组**整个覆盖**成数字：

   | 位置 | 代码 | 后果 |
   |---|---|---|
   | `public/app.js:1193` | `trace.ops[idx] = { ...trace.ops[idx], ...summary, summary, updatedAt }` | SSE 收到 `op-end` 后，该操作的 `nodes` 变数字 |
   | `public/app.js:1520` | `trace.ops[idx] = { ...trace.ops[idx], ...s, summary: s, updatedAt }` | 打开追踪页拉 `/debug/ops` 后，**所有**操作 `nodes` 变数字 |

4. 之后 SSE 再来任何一条 `node` 帧 → `app.js:1174 op.nodes.push(...)` 立刻抛错。
5. 为什么每次都必崩：实测相邻崩溃间隔为 `292s / 10.2s / 233s / 54s / 30s / 20s / 36s / 64s / 52s / 72s / 83s …`——**最短仅 10.2 秒**，而日志去重窗口正好 10 秒。也就是说真实崩溃频率比日志记录的 19 次更高，只是被 `logger.js` 的 `DEFAULT_DEDUP_MS = 10s` 折叠了（`dedup_key` 去重后只剩 **1** 个）。
6. **用户可见后果**：开着追踪 → 打开「跟踪」页 → 实时流一有节点就整帧崩溃 → **实时操作列表再无数据**，而界面不会给出任何提示。这解释了记录里 `trace-open` 出现 4 次（13:54:35/40/41/44）——用户反复点开想看，每次都被崩掉。

**影响面**：不只是「面板显示坏掉」。`traceHandleStreamItem` 是 `es.onmessage` 的直接调用者，抛出的异常逃逸到事件循环，成为未捕获异常；同时把"实时追踪"这个核心能力变成了摆设。

**复现（已执行，见第四节）**：
```
merged = { ...{ nodes: [1,2,3] }, ...{ nodes: 6 } }
merged.nodes = 6 | typeof = number
REPRODUCED CRASH -> TypeError: merged.nodes.push is not a function
```

### D2（严重）时钟域混用 → 每个 AI 节点 / 慢通道节点的耗时都是负数

**证据**

- 12 个 `harness` 节点、6 个 `ai` 节点，`cost_ms` 全部落在 `-1787397288754 ~ -1787397456266` 区间，例如：

  | seq | 节点 | 记录值 |
  |---|---|---|
  | 64 | `callAI`（deepseek-flash） | `-1787397454571ms` |
  | 583 | `callAIStream`（上下文 2174 / 输出 5802 tokens） | `-1787397422751ms` |
  | 614 | `harness 任务（慢通道）` | `-1787397452761ms` |

- 量级解读：`-1.787e12 ms ≈ 56.7 年` = 开机时间 − Unix 纪元时间。**根因是两套时钟相减**：

  | 供时方 | 取值方式 | 含义 |
  |---|---|---|
  | `debug-trace.js:73 nowMs()` | `process.hrtime.bigint() / 1e6` | 开机以来的毫秒 |
  | `harness.js:377` `traceT0 = Date.now()` | `Date.now()` | Unix 纪元毫秒 |
  | `server.js:562` / `server.js:688` `const t0 = Date.now()` | `Date.now()` | Unix 纪元毫秒 |

  消费端 `debug-trace.js:709 / 735` 固定做 `nowMs() - t0`，于是每一笔都变成那个巨大的负数。

- **最贵的两笔恰好中招**：`callAIStream` 7976 tokens、`compressStoryMemory` 58500ms 这两类节点，正是用户最想看的数据，全部不可读。

### D3（严重）服务端发起的操作根本不会被关闭 → 时间被伪造到「停录那一刻」

**证据（隔离实例实测，非推断）**

在沙箱实例（端口 3799、独立数据目录）上录一次真实请求：

```
GET /api/search?q=天&work_id=15   （带 X-Trace-Op）
→ 请求正常返回，400ms 后查询 /api/debug/ops：
   probe-op-1 | probe client op | status=running | cost_ms=0 | nodes=0 | ended_at=""
停录后 JSONL：
   op-end  auto_closed=true  cost_ms=485  status=done
```

请求早已结束、节点也落了 6 条，**但没有任何代码把这条操作关掉**：唯一会收尾它的是 `stopTracing` 的兜底循环（`debug-trace.js:397-404`），而那时距操作真正结束已经过去整个会话的时长。

**真实记录上的后果**：

| 操作 | 节点时间线实际跨度 | 记录声称 | 放大倍数 |
|---|---|---|---|
| `GET /api/search`（30ms 的检索） | 30ms | **546469ms** | 18215× |
| `GET /api/novel/context`（2ms 的缓存命中装配） | 2ms | **546424ms** | 273212× |

而且这两条被标成 `status: done`，唯一的"这条记录不可信"标记 `auto_closed: true` **前端从头到尾没有展示**（`public/app.js` 全文无 `auto_closed`）。

**附带同源问题**：`app.js:1082` 的 `close` 分支用 `res.statusCode || 499` 记录中止，但 `res.headersSent` 为真时 `statusCode` 就是 200——**客户端中断会被记成 200**。本会话里 12 分钟任务被取消、`write_stream` 被 abort，这些失败在追踪里看不到任何痕迹。

### D4（中等）客户端自报耗时与后端节点时间线互不校验 → 记录自相矛盾

**证据**（同一次用户点击，三份证据互相打脸）：

| 来源 | 值 |
|---|---|
| 追踪摘要 `ui-ce102987… compress-story-memory` | `cost_ms = 2632` |
| 同一操作的 13 个节点时间线 | `13:41:50.369Z → 13:42:48.872Z` = **58503ms** |
| `server.js:2686` 的 `compressStoryMemory` 函数节点 | `cost=58500ms` |
| 服务端慢请求日志 | `POST /api/story_memory/compress 耗时 58501ms` |
| 前端慢 API 日志 | `API /story_memory/compress 耗时 58506ms` |

第二次点击更夸张：摘要 `7656ms`，节点跨度 `89362ms`，日志 `89366ms`（**11.7 倍**）。

**机理**：操作耗时存在**三个互不相认的算源**——
- 前端 `app.js:995` `performance.now() - trace.opStartedAt`，但只在"点击处理链 promise 结束"或"10 秒心跳"时结算，长任务中它算出的只是**到结算那一刻为止**的值；
- 后端 `debug-trace.js:497` `Math.max(op.costMs, nowMs() - op.t0)`；
- 展示层直接取摘要。

没有任何一处用**该操作实际累积的节点时间线**去校验或修正耗时，所以一个 58 秒的同步 AI 任务可以在记录里显示成 2.6 秒，而同一份记录里的函数节点和日志都写着 58.5 秒。

**它为什么危害大**：这正是用户做性能复盘时要看的第一列数字。工具在"耗时"这一项上系统性低报，等于把最核心的诊断价值抵消掉。

### D5（中等）错误被藏起来：有 error 节点，摘要却写 `errors: 0`

**证据**（同一份记录里两条操作都如此）：

| 操作 | 节点里的失败 | 摘要声称 |
|---|---|---|
| `task-90641dad…`（小说设定 AI 生成） | `PUT /novel/chapter_blueprint` → **error「蓝图内容不能为空」** | `errors: 0` |
| `ui-b1248764…`（ai-task-cancel） | `harness 任务（慢通道）` → **error「Harness 任务已取消」** | op 摘要 `errors: 1`，但 **session 级 `errors: 2`** |

**机理**：`errors` 是"追加节点那一刻"累加的计数器，只代表建摘要时的事实。这两类 error 节点都是**收尾之后才到**的（客户端补挂 / 迟到节点），从此不在任何摘要里体现。列表上和"只看错误"筛选里，这两条操作看起来是**完全成功**的。

**为什么要紧**：追踪工具的第一职责是**让人看见失败**。现在它会系统性地把"操作内的失败"洗成成功，而用户开着追踪正是为了复盘失败。

## 五、整改意见与本次实施

### 5.1 整改意见（逐条对应缺陷）

| 缺陷 | 整改意见 | 判据（改完怎么算对） |
|---|---|---|
| D1 数组被计数覆盖 | 前端新增唯一入口 `normalizeTraceSummary()`：合并前把后端摘要的 `nodes`（计数）改名为 `nodeCount`，**保留本地 `nodes` 数组**；两处合并点统一走它；`traceHandleStreamItem` 加类型兜底 | 摘要到达后再来节点帧不抛错；合并服务端摘要后本地已收节点不丢失 |
| D2 时钟域混用 | `debug-trace.js` 导出**唯一时钟** `traceNow()`；所有要把 `t0` 喂给埋点的调用方必须用它；启动时自检「单调时钟 vs 纪元时钟」并在异常时告警 | 每个 AI / 慢通道节点的 `cost_ms` 都是正数；日志出现 `trace_clock_ok` |
| D3 操作无人关闭 | 追踪器自己做**空闲收尾**：记录 `lastActivityAt`，当「无在途请求 + 空闲超宽限期」时主动 `finishOperation` 并置 `auto_closed`；同时修 499 判定让中断可见 | 服务端自发请求在秒级内自动收尾，不再挂到停录；被中断的请求显示为 cancelled 而非 200 |
| D4 耗时三源不一致 | 耗时以**服务端时钟**为准（客户端值只作参考），并把"这条耗时是不是补出来的"用 `auto_closed` 显式标出；跨时钟域的垃圾耗时用 `cost_untrusted` 兜底 | 摘要耗时不再出现 11.7 倍低报；界面能区分测量值与补值 |
| D5 错误被藏 | `opSummary` 按**节点事实**重算 `errors`（累加值只作下限），`status` 在 `errors > 0` 且原为 `done` 时升为 `error`；前端列表级 `errors` 取摘要与本地节点的较大者 | 含 error 节点的操作在列表和"只看错误"筛选里都可见 |

**总原则**：任何会展示给用户的数字，旁边必须有"这个数字可不可信"的标记；没有标记的补值，比没有值更危险。

### 5.3 必须说明的行为取舍（不是"顺手改好了"，是权衡）

1. **服务端自发操作改为"空闲 1200ms 后自动收尾"**，收尾精度 ≈ 1200ms + 一个 200ms tick ≈ **1.2～1.4 秒**。
   - 相比旧行为（一直挂到停录：30ms 记成 546469ms）是数量级修正，但**仍不是精确耗时**，因此这类记录一律带 `auto_closed: true`，界面明确标注——**宁可承认"这是补的收尾"，也不假装精确**。
   - 为什么不做得更准：服务端无法知道"业务真的做完了"。要精确只能由发起方显式结束，那是更大的改动，留待后续。
2. **`auto_closed` 的语义严格限定为"追踪器主动补的收尾"**。前端正常收尾的操作**不会**被打上这个标记（实测：带 `X-Trace-Op` 的请求由前端 `/debug/op` 正常结束 → `auto_closed=false`）。若前端上报迟到超过 1.2 秒，服务器会先自动收尾、随后忽略客户端的重复收尾（幂等），此时该操作带 `auto_closed`——代价是这条的耗时不代表前端视角的真实耗时，收益是绝不出现"挂着不关的假耗时"。
3. **中途中断的请求现在会显式记为 `status: cancelled`**（`http_status: 499`），不再被 200 掩盖。这会**让错误/取消类操作变得可见**，看起来"多出了失败"，实际是本来就存在的失败第一次被如实记录。
4. **`cost_untrusted` 是兜底开关**：只要操作内出现 `|cost| > 1 天` 的节点，界面就打「耗时不可信」。它是给"以后再有人接错时钟"准备的告警，不是本轮修复的替代。

### 5.4 未做（明确不做，避免过度修复）

- **不给服务端加白名单**去区分"哪些服务端操作需要收尾"。实测里 `anon-*` 操作几乎都是"请求完就结束"，加白名单只会引入"漏收尾"的新风险。
- **不改 `traceSendOp` 的 payload 形状**（前端仍上报 `cost_ms`，服务端仍以自己的时钟为准）。改协议要动两边 + 测试，收益不抵风险。
- **不改 `logger.js` 的 10 秒去重窗口**（O6 只做了前端帧级上报，去重策略本身留作后续），因为它影响的是所有日志而不只是追踪。

## 八、给下一轮的检查清单（可复用）

1. **同名不同型**：任何 `{ ...a, ...b }` 的合并，先列出两边**同名字段的类型**；`nodes`/`count`/`size` 这类"数量 vs 集合"是重灾区。
2. **时间只有一个出口**：跨模块传时间戳时，问"这是同一个时钟域吗"；不同域相减产生的巨大数量级（±1e12ms）应当能被自动识别——本轮已加 `cost_untrusted` 兜底。
3. **关灯顺序之外还要问"谁负责关灯"**：第二轮修的是"先关灯后收尾"，本轮暴露的是"根本没人收尾"。任何有 `begin` 的结构，必须能回答"谁调 `finish`，他不调会怎样"。
4. **摘要字段要能自证可信度**：一个数字旁边必须有"这个数字可不可信"的标记（`auto_closed` / `cost_untrusted`），否则用户会把补出来的值当测量值用。
5. **`errors` 必须以事实重算，不能只累加**：计数器和事实会分叉；读取时按事实重算，累加值只作下限。
6. **清理只清自己**：只终止自己启动的进程/端口（按 job 或 PID），**永远不要按进程名全量终止**（D-5 的教训）。
