## 二、逐项判定

### CR-1 · settings 档预算常量过期

- **现象与证据**：`computeFloor('settings')` 实测 **18,173**，而 `TOTAL_BUDGET.settings` 是 **18,000**——
  「可执行下限 < 总预算」这条不变量为假。两个下游同时报红：`.p1-baseline/test-assembler.mjs` 的
  「预算可达」断言、`verify-all` 的「契约文档数字与活规格一致」。
- **根因**：上一轮新增 `terms` 层（相关设定词条，cap 800）时，**没有重算 settings 档的下限**。
  下限从 17,356 涨到 18,173，静默越过常量——这正是契约里「凡设预算常量，先算可执行下限」那条规则要防的事。
- **候选方案**：
  - A 抬预算到 19,000（下限 + 827 余量，与上一版 18,000 相对 17,356 的 644 余量同量级）→ 质量影响 `NONE`。
  - B 把 `terms` 改成可收缩层（floor 400）→ 下限降到 17,773，代价是**最需要词条的设定类生成**在大作品下被压到 400 字（质量损失 `LOW–MEDIUM`）。
  - C 压小某个质量层的 cap 去迁就旧常量 → 任意选一个层挨刀，等于拿真实内容换形式达标（§14 明令禁止）。
- **判定**：**规则 1**（修改不降低整体质量 → 修改并采用最优方案）+ §10（最小必要修改＝改常量，不动层规格）→ **A**。
- **执行**：`ai/context/layers.mjs` 的 `TOTAL_BUDGET` 改为 `{ settings: 19000, default: 26000 }`，
  注释里写明本次校正的算术与理由。**没有改任何层的 cap**。
- **验证**：`test-assembler` 32/32；`verify-all` 的两条对账转绿；插件冒烟 39/39（大作品 settings 仍收敛，
  断言由 18,000 同步为 19,000）。

### CR-2 · 文档与断言数字漂移

- **现象**：`docs/context-contract.md` 的表格与 `docs/ai-core.md`、插件 `README`/`ENGINE.md` 里写着
  **20,547 / 17,356**（上一版下限）；`verify-all` 会去文档里找**活规格**的数字，找不到就判红。
- **判定**：与 CR-1 同根因，属「执行 CR-1 的必要范围」（§10：解决当前问题所必需的最小范围）。
- **执行**：文档数字改为 **21,364 / 18,173**，表格按 `computeFloor()` 的四个分项（不收缩层 / 弹性层下限 /
  标题+分隔 / 截断提示）重算；补一条「加层的同一轮就要重算下限」的教训；插件 `smoke.mjs` 的断言改为
  **从常量派生**（不再手写数字）。历史报告（`docs/context-optimization-*.md` 等）**不动**——
  它们记录的是当时的事实。

### CR-3 · `app_logs` 差集判据的假警

- **现象与证据**：`verify-all` 长期红：「真实库有 113 行在副本中找不到 —— 需要进一步排查真实库是否被写过」。
  追下去：副本停在 **9/20** 的采样，真实库多出的 113 行是 **9/21** 的正常活动
  （`harness/task_start`、`服务启动`、`工具配置已加载`…）+ 用户自己用过的「清空日志」留下的空档。
- **判据错在哪**：副本是**某一次采样**的快照，而真实库是活的——「真实库有、副本没有」在正常使用下必然 >0。
  把它一律判成「真实库被删」等于**每次都用一条假警去换注意力**。
- **候选方案**：
  - A 重新采样副本（复制真实库过去）→ 立刻绿，但应用一写日志又会红（治标，且掩盖判据本身的错）。
  - B 用 **id 顺序**拆分差集：`id > 副本最大 id` = 采样后新增（正常，不判红）；
    `id ≤ 副本最大 id` 却缺失 = 两库分叉/被改写（判红）；新增行里带**探针特征**（`verify-`/`probe-`/`.p1-baseline/`…）也判红——那正是 2026-09-15 事故的形态。
  - C 删掉这条检查 → 失去事故留痕（§14：不能为了形式上好看而牺牲检查能力）。
- **判定**：**规则 3**（修改会降低检查的宽泛度，但现状影响实际使用：红灯失去意义）+ §10 → **B**。
  关键约束：**不许为了让检查变绿而放宽判据**——所以同时**新增**两个判红条件，并加双向自检。
- **执行**：`.p1-baseline/diff-log-noise.mjs` 重写判据（`classifyLogDiff` + `judgeLogDiff` 纯函数、`--self-test`）；
  `verify-all` 的条目改名为「真实库未被删改（app_logs 差集归因；正常增长不判红）」并挂上自检。
- **验证**：自检 3/3（正常增长不判红 / 探针写入判红 / 分叉判红）；真实库上 exit 0，
  并打印那 113 行的具体来源供人核对（不是「静默放行」）。

### CR-4 · 篇幅的权威口径（原 D11）

- **现象**：同一章存在三套目标——章节 `target_words=3000`、作品 `default_chapter_words=4000`、
  风格文本「单章 3000～5000 字（默认 4000）」。写作路径按**章节目标**补足，审稿却按**风格文本**判，
  于是 work#18 第 5、6 章反复出现「篇幅不足」——**一条由口径不一致制造、却被记成正文问题的假 issue**。
- **真实目标识别（§9）**：作者要的不是「改数据」，而是**别再报这条假 issue**。
- **候选方案**：
  - A 统一作品数据（改 `target_words` / 作品默认 / 风格文本）→ 动的是**创作数据**，且「以哪一套为准」属作者口径（不可逆方向不明）。
  - B 把**与写作路径同源**的权威值（章节覆盖 > 作品默认）写进审稿提示词 → 质量无损失、可逆、局部。
  - C 什么都不做，只靠预检的 info 提示 → 不解决误报。
- **判定**：**规则 1** → **B**。A 不做：§13「仍不确定时优先可逆、局部、低风险」——
  数据统一继续留在 `docs/pending-decisions.md` 的 D11 等作者点头，工具不替作者做数据决策。
- **执行**：`public/app.js`（`resolveTargetWords(chapterId)` 支持按章解析 + `buildAIReviewPrompt` 第 4 个参数 +
  审稿调用点传入）；`frontend-test.mjs` 新增两条断言（有目标时必须声明、拿不到目标时不编造数字）。
- **验证**：前端执行验证 ALL PASS（含新增的 `98e/98f`）。

### CR-5 / CR-6 / CR-7 · 三项 KEEP_CURRENT 的理由

- **CR-5 剧情线停滞阈值（4 章）**：改它等于换一套判断标准，而**没有证据说 4 不对**
  （它是 4000 字/章长章下的保守值，且在真实作品上只报 info 级）。§5 规则 2 → 保持现状；
  作者想改随时改 `continuity_thresholds:<workId>`，**不需要改代码**。
- **CR-6 系统出场判据（字面命中近似）**：近似是已知的，但噪声已被两件事压住：
  刚好过线只报 `info`、达到上限 1.5 倍才升 `warning`；且 finding 带证据（命中数/上限）可一键豁免。
  要做「按发言块计数」，先得定义「什么算一次出场」——那属于**缺失的关键信息**（§13 的询问例外），
  但当前默认值并不影响使用，所以**不升级为询问**，只保留为可覆盖口径。
- **CR-7 角色卡时点（原 D12）**：现状影响是真实的（生成端照着卡写会写出时点错置），
  但**更优替代方案已落地**：预检逐章报「角色卡时点越界」并可豁免（§9：识别真实目标→选能实现同目标的替代方案）。
  改卡本身是不可逆的创作数据变更；若改成「按章裁剪卡的状态」，会让 `verify-all` 的**逐字节装配回归**
  失去意义（质量影响 `MEDIUM`）→ §10 最小必要修改：**不动**。需要作者点头的只剩「卡怎么写」。

## 四、没做的事（对照 §14「禁止行为」）

1. **没有因为「用户说要优化」就大改**：三项 KEEP_CURRENT 的判定与执行同样是被要求的产出。
2. **没有把偏好当使用问题**：阈值类（停滞章数、出场判据）属作者口径，一律 KEEP + 保留覆盖入口。
3. **没有为了形式上满足而牺牲质量**：CR-1 拒绝「压小质量层去迁就旧常量」，CR-3 拒绝「删掉那条红检查」。
4. **没有忽略真实使用障碍**：CR-3、CR-4 都是「红灯/假 issue 影响实际判断」的现实问题，照规则 3 修了。
5. **没有机械照搬表面方案**：CR-4 里原本问的是「以哪一套数据为准」，实际落地的是「让审稿与写作同源」——
   同一目标的更小改动。
6. **没有解决小问题引出新问题**：CR-3 改判据时**同时**加了两个判红条件与双向自检，检出能力只增不减。
7. **没有用一项的收益去合理化另一项的损失**：7 项各自独立判定（§11 多确认项处理）。
8. **没有改任何作品数据**：`chapters.target_words`、`default_chapter_words`、角色卡、`style_positive` 一律原样。
