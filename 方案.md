# DeepSeek Harness OpenViking 插件实现方案

## 1. 目标

为 DeepSeek Harness 实现一个独立的 OpenViking 检测插件，不修改 Harness
主仓库。

插件需要实现：

-   在 Harness 插件/设置界面提供 OpenViking 管理入口。
-   UI 风格复用 Harness 现有设置组件，保持一致。
-   打开页面时自动检测 OpenViking 服务是否已经启动。
-   服务已启动时显示真实运行状态。
-   服务未启动时提供启动开关。
-   用户开启开关后，由 Host 端启动 OpenViking 服务。
-   启动后通过健康检查确认服务真正可用，再更新 UI。
-   支持停止由插件自身启动的 OpenViking 服务。
-   外部启动的 OpenViking 只检测，不随意终止。
-   支持启动失败、超时、进程退出等异常状态。

------------------------------------------------------------------------

## 2. 插件目录结构

建议插件名称：

``` text
dsh-plugin-openviking/
├── package.json
├── cordis.patch.yml
├── tsconfig.json
└── src/
    ├── index.ts
    ├── openviking.ts
    ├── remote.ts
    └── client/
        ├── index.ts
        └── OpenViking.vue
```

各文件职责：

-   `src/index.ts`：Host 插件入口、配置注册、生命周期管理。
-   `src/openviking.ts`：OpenViking 状态检测、启动、停止及进程管理。
-   `src/remote.ts`：向 Browser/UI 暴露运行时 API。
-   `src/client/index.ts`：Browser 插件入口，注册设置/配置页面。
-   `src/client/OpenViking.vue`：OpenViking 设置 UI。

------------------------------------------------------------------------

## 3. 总体架构

``` text
Harness Settings / Plugin UI
            │
            │ Remote API
            ▼
   OpenViking Host Plugin
            │
       ┌────┴─────┐
       │          │
       ▼          ▼
 Health Check   child_process
       │          │
       └────┬─────┘
            ▼
       OpenViking
```

原则：

1.  Vue/UI 层不直接启动本地进程。
2.  UI 不直接访问 OpenViking localhost 接口。
3.  所有服务管理都放在 Host 插件中。
4.  UI 通过 Harness 的 Host/Browser 通信机制调用 Host。
5.  UI 状态始终以真实服务检测结果为准。

------------------------------------------------------------------------

## 4. 服务状态模型

定义统一状态：

``` ts
export type OpenVikingStatus =
  | 'checking'
  | 'running'
  | 'stopped'
  | 'starting'
  | 'stopping'
  | 'error'

export interface OpenVikingState {
  status: OpenVikingStatus
  endpoint: string
  pid?: number
  owned?: boolean
  error?: string
}
```

状态含义：

  状态         含义
  ------------ --------------------------
  `checking`   正在检测 OpenViking
  `running`    服务健康检查成功
  `stopped`    服务未运行
  `starting`   插件正在启动服务
  `stopping`   插件正在停止服务
  `error`      检测、启动或停止出现错误

`owned` 用于区分服务是否由当前插件实例启动。

------------------------------------------------------------------------

## 5. OpenViking Manager

在 `src/openviking.ts` 中实现服务管理类。

建议核心接口：

``` ts
class OpenVikingManager {
  async status(): Promise<OpenVikingState>
  async refresh(): Promise<OpenVikingState>
  async start(): Promise<OpenVikingState>
  async stop(): Promise<OpenVikingState>
  async dispose(): Promise<void>
}
```

Manager 内部维护：

``` ts
private ownedProcess?: ChildProcess
private state: OpenVikingState
```

其中 `ownedProcess` 非常重要。

只有插件自己通过 `spawn()` 创建的进程才能被插件主动终止。

------------------------------------------------------------------------

## 6. 自动检测 OpenViking

不要仅根据 PID 或进程名称判断 OpenViking 是否运行。

优先使用 OpenViking 提供的健康检查接口或一个稳定的 HTTP API。

示例：

``` ts
async function checkOpenViking(): Promise<boolean> {
  try {
    const response = await fetch(HEALTH_URL, {
      signal: AbortSignal.timeout(2000),
    })

    return response.ok
  } catch {
    return false
  }
}
```

插件加载：

``` text
Harness 启动
    ↓
加载 OpenViking Plugin
    ↓
manager.refresh()
    ↓
调用 Health Check
    ↓
┌────────────────┬────────────────┐
│ 可访问          │ 不可访问        │
│ running        │ stopped        │
└────────────────┴────────────────┘
```

这样即使用户通过终端、systemd、Docker 或其他方式启动了
OpenViking，插件仍能识别真实状态。

------------------------------------------------------------------------

## 7. 启动 OpenViking

用户打开开关后调用：

``` ts
manager.start()
```

首先防止重复启动：

``` ts
if (await checkOpenViking()) {
  return currentRunningState
}
```

随后启动 OpenViking：

``` ts
import { spawn } from 'node:child_process'

this.ownedProcess = spawn(
  config.command,
  ['serve'],
  {
    stdio: ['ignore', 'pipe', 'pipe'],
    detached: false,
  },
)
```

实际命令及参数应根据 OpenViking 的正式 CLI
调整，并放入配置，而不是散落在 UI 中。

记录 stdout/stderr：

``` ts
this.ownedProcess.stdout?.on('data', data => {
  console.log(`[OpenViking] ${data}`)
})

this.ownedProcess.stderr?.on('data', data => {
  console.error(`[OpenViking] ${data}`)
})
```

------------------------------------------------------------------------

## 8. 启动后健康检查

`spawn()` 成功并不等于 OpenViking 已经可用。

启动后循环检测：

``` ts
async function waitUntilHealthy() {
  const deadline = Date.now() + config.startupTimeout

  while (Date.now() < deadline) {
    if (await checkOpenViking()) {
      return
    }

    await new Promise(resolve => setTimeout(resolve, 500))
  }

  throw new Error('OpenViking startup timeout')
}
```

状态流：

``` text
stopped
   ↓
用户开启
   ↓
starting
   ↓
spawn OpenViking
   ↓
循环 Health Check
   ├── 成功 ──→ running
   └── 超时 ──→ error
```

如果子进程在健康检查成功前退出，也应立即进入 `error`
状态，而不是继续等待完整超时时间。

------------------------------------------------------------------------

## 9. 停止服务

关闭开关时：

``` ts
manager.stop()
```

先判断服务来源。

### 插件启动的服务

存在：

``` ts
this.ownedProcess
```

则允许终止：

``` ts
this.ownedProcess.kill()
```

之后循环健康检查，直到服务不可访问，再返回：

``` text
stopped
```

### 外部启动的服务

如果健康检查发现服务运行，但：

``` ts
this.ownedProcess === undefined
```

说明 OpenViking 不是当前插件启动的。

推荐：

-   显示「服务已运行（外部）」。
-   不允许插件直接 kill。
-   避免通过进程名查找并强杀进程。

这样可以防止插件误杀用户手动运行、Docker 运行或由系统服务管理器运行的
OpenViking。

------------------------------------------------------------------------

## 10. Host 生命周期

插件入口：

``` ts
export async function apply(ctx: Context, config: Config) {
  const manager = new OpenVikingManager(config)

  await manager.refresh()

  registerOpenVikingRemote(ctx, manager)

  ctx.effect(() => {
    return () => {
      manager.dispose()
    }
  })
}
```

插件卸载时：

-   清理监听器。
-   释放资源。
-   根据产品策略决定是否停止插件自己启动的 OpenViking。
-   绝对不要停止外部 OpenViking。

------------------------------------------------------------------------

## 11. Remote API

Host 向 Browser/UI 暴露最小 API：

``` ts
status(): Promise<OpenVikingState>

start(): Promise<OpenVikingState>

stop(): Promise<OpenVikingState>
```

可进一步增加：

``` ts
restart(): Promise<OpenVikingState>
```

但第一版并非必需。

UI 不应该直接调用：

``` ts
fetch('http://127.0.0.1:xxxx')
```

原因包括：

-   CORS。
-   Browser 与 Host 网络环境可能不同。
-   Desktop/Web 部署方式可能不同。
-   无法可靠判断进程所有权。
-   浏览器不能安全启动本机进程。

------------------------------------------------------------------------

## 12. Settings UI

使用 Harness 已有设置组件和样式，不重新设计一套 UI。

示意：

``` vue
<template>
  <SettingItem
    title="OpenViking"
    description="OpenViking 知识库服务"
  >
    <Switch
      :model-value="state.status === 'running'"
      :disabled="busy || isExternal"
      @update:model-value="toggle"
    />
  </SettingItem>

  <div class="status">
    {{ statusText }}
  </div>
</template>
```

状态文字：

``` ts
const statusText = computed(() => {
  switch (state.value.status) {
    case 'checking':
      return '正在检测 OpenViking 服务…'

    case 'starting':
      return '正在启动 OpenViking…'

    case 'stopping':
      return '正在停止 OpenViking…'

    case 'running':
      return state.value.owned
        ? 'OpenViking 服务已启动'
        : 'OpenViking 服务已运行（外部）'

    case 'stopped':
      return 'OpenViking 服务未启动'

    case 'error':
      return state.value.error ?? 'OpenViking 操作失败'
  }
})
```

## 13. 开关行为

不要使用「乐观更新」。

错误：

``` ts
enabled.value = true
await api.start()
```

因为如果启动失败，UI 会暂时显示错误状态。

正确方式：

``` ts
async function toggle(enabled: boolean) {
  busy.value = true

  try {
    state.value = enabled
      ? await api.start()
      : await api.stop()
  } catch (error) {
    // 展示错误
  } finally {
    state.value = await api.status()
    busy.value = false
  }
}
```

整个流程：

``` text
用户打开开关
      ↓
Switch disabled / loading
      ↓
Remote API
      ↓
Host start()
      ↓
spawn OpenViking
      ↓
Health Check
      ↓
返回真实状态
      ↓
更新 Switch
```

开关代表的是：

> OpenViking 当前真实运行状态

而不是：

> 用户曾经点击过"开启"。

------------------------------------------------------------------------

## 14. 插件配置

建议配置：

``` ts
export interface Config {
  command: string
  args: string[]
  endpoint: string
  startupTimeout: number
  healthCheckTimeout: number
}
```

例如：

``` ts
export const Config = Schema.object({
  command: Schema.string()
    .default('openviking'),

  endpoint: Schema.string()
    .default('http://127.0.0.1:PORT'),

  startupTimeout: Schema.number()
    .default(15000),

  healthCheckTimeout: Schema.number()
    .default(2000),
})
```

其中具体端口、CLI 参数和健康检查路径需要以目标 OpenViking
版本的实际接口为准。

------------------------------------------------------------------------

## 15. 不要把运行状态当成 Config

不推荐：

``` ts
Config {
  enabled: boolean
}
```

因为 `enabled` 实际表示运行时状态，而不是静态插件配置。

应该分成三层：

``` text
Plugin Config
├── command
├── args
├── endpoint
├── startupTimeout
└── healthCheckTimeout

Runtime State
├── checking
├── starting
├── running
├── stopping
├── stopped
└── error

Runtime Actions
├── status()
├── start()
└── stop()
```

这样可以避免修改配置导致插件重载后出现状态混乱。

------------------------------------------------------------------------

## 16. 并发控制

必须防止用户快速连续点击开关造成：

``` text
start()
start()
stop()
start()
```

建议 Manager 内增加操作锁：

``` ts
private operation?: Promise<OpenVikingState>
```

当启动或停止正在执行时：

-   UI 禁止重复操作。
-   Host 也拒绝或合并重复请求。

不能只依赖前端 `disabled`，Host 必须自己保证并发安全。

------------------------------------------------------------------------

## 17. 进程异常退出

注册：

``` ts
process.on('exit', ...)
process.on('error', ...)
```

如果插件启动的 OpenViking 意外退出：

``` text
running
   ↓
process exit
   ↓
重新 Health Check
   ↓
stopped / error
```

前端下一次查询状态时即可获得真实结果。

如果 Harness 的 Browser/Host
通信支持事件推送，可以进一步把状态变化主动推送给
UI；第一版也可以采用进入页面和操作后主动刷新。

## 19. 推荐开发顺序

### 第一阶段：Host

先完成：

1.  `OpenVikingManager`
2.  `checkOpenViking()`
3.  `start()`
4.  `stop()`
5.  `waitUntilHealthy()`
6.  子进程生命周期
7.  外部进程识别
8.  并发控制

先通过日志或测试确认：

``` text
未启动 → 检测 stopped
启动 → running
停止 → stopped
外部启动 → running + owned=false
启动失败 → error
```

### 第二阶段：Remote API

实现：

``` text
status
start
stop
```

确保 Browser 可以正常调用 Host。

### 第三阶段：UI

最后添加：

-   OpenViking 设置入口。
-   状态文字。
-   Switch。
-   loading。
-   error。
-   外部服务提示。

这样调试成本最低。

------------------------------------------------------------------------

## 20. 验收标准

插件完成后至少测试以下场景：

-   Harness 启动，OpenViking 未运行：显示 OFF。
-   Harness 启动前 OpenViking 已运行：自动显示 ON。
-   点击 ON：OpenViking 成功启动，健康检查通过后显示 ON。
-   OpenViking 启动失败：显示 OFF 和错误原因。
-   OpenViking 启动超时：显示明确超时错误。
-   快速重复点击：不会启动多个 OpenViking。
-   点击 OFF：插件自身启动的 OpenViking 被正常停止。
-   外部 OpenViking：插件不会误杀。
-   OpenViking 意外退出：后续状态检测能恢复为 stopped/error。
-   插件卸载：资源和监听器被正确释放。
-   Harness UI 风格、间距、Switch 等与现有设置页保持一致。

------------------------------------------------------------------------

## 21. 核心原则总结

整个插件遵循四条原则：

1.  **UI 只负责展示和发出操作请求。**
2.  **Host 负责 OpenViking 的检测、启动、停止和生命周期。**
3.  **开关永远反映真实服务状态，以 Health Check 为最终依据。**
4.  **只管理插件自己创建的进程，不误杀外部 OpenViking。**

最终实现为一个独立插件包：

``` text
DeepSeek Harness
       +
dsh-plugin-openviking
       ↓
自动检测 OpenViking
       ↓
设置页面展示真实状态
       ↓
一键启动/停止插件托管的 OpenViking
```

无需修改 DeepSeek Harness 主项目源码。
